## 1. VM vs Container

### Virtual Machine
A VM is a virtual computer running through a hypervisor. Each VM normally has its own guest operating system.

```text
Physical Server
└── Hypervisor
    ├── VM 1 → Guest OS → Application
    ├── VM 2 → Guest OS → Application
    └── VM 3 → Guest OS → Application
```

### Container
A container packages an application and its dependencies while sharing the host OS kernel.

```text
Host OS
└── Docker Engine
    ├── Container 1 → App A
    ├── Container 2 → App B
    └── Container 3 → App C
```

### Comparison

| Feature | VM | Container |
|---|---|---|
| Virtualizes | Hardware/system | OS-level environment |
| Guest OS | Yes | No separate full guest OS |
| Startup | Usually slower | Usually faster |
| Size | Usually GBs | Often MBs |
| Resource usage | Higher | Lower |
| Isolation | Strong | Process-level |
| Density | Lower | Higher |
| Typical use | Traditional applications | Microservices, CI/CD, cloud-native apps |

# 5. Dockerfile

A Dockerfile contains instructions used to build an image.

Example:

```dockerfile
FROM nginx:latest

COPY index.html /usr/share/nginx/html/index.html

EXPOSE 80

CMD ["nginx", "-g", "daemon off;"]
```

## Common instructions

### FROM

```dockerfile
FROM ubuntu:24.04
```

Specifies the base image.

### RUN

Executes commands during image build.

```dockerfile
RUN apt-get update
RUN apt-get install -y curl
```

### COPY

Copies files from the build context.

```dockerfile
COPY app.py /app/app.py
```

### ADD

Similar to COPY but has additional features. Prefer COPY for normal file copying.

### WORKDIR

Sets the working directory.

```dockerfile
WORKDIR /app
```

### ENV

Sets environment variables.

```dockerfile
ENV APP_ENV=production
```

### EXPOSE

Documents the container port.

```dockerfile
EXPOSE 8080
```

`EXPOSE` does not publish the port. Publishing is done with `-p`.

### CMD

Default command or arguments.

```dockerfile
CMD ["python", "app.py"]
```

### ENTRYPOINT

Defines the main executable.

```dockerfile
ENTRYPOINT ["python"]
```

### CMD vs ENTRYPOINT

```dockerfile
ENTRYPOINT ["python"]
CMD ["app.py"]
```

Running:

```bash
docker run myimage
```

results in:

```text
python app.py
```

# 9. Docker Network Types

Main Docker network drivers:

1. Bridge
2. Host
3. None
4. Overlay
5. Macvlan
6. IPvlan

## Bridge

Most common network for containers on one Docker host.

```bash
docker network create mynetwork
docker run -d --name app --network mynetwork nginx
```

Containers on the same user-defined bridge can communicate using container names.

```text
Container A ---> Container B
       \          /
        \-- bridge
```

## Host

Container shares the host network namespace.

```bash
docker run --network host nginx
```

## None

No normal network connectivity.

```bash
docker run --network none alpine
```

Useful for isolation.

## Overlay

Connects containers/services across multiple Docker hosts, especially with Docker Swarm.

```text
Host 1                      Host 2
Container A ---- overlay ---- Container B
```

## Macvlan

Allows a container to appear as a separate network device on the physical network.

## IPvlan

Provides advanced IP-based networking using the parent interface.

### Network commands

```bash
docker network ls
docker network create mynet
docker network inspect mynet
docker network connect mynet web
docker network disconnect mynet web
docker network rm mynet
```

# 10. Docker Storage Types

Containers are generally ephemeral. Data stored only in a container's writable layer can disappear when the container is removed.

Main storage mechanisms:

1. Volumes
2. Bind mounts
3. tmpfs

## Volumes

Docker-managed persistent storage.

```bash
docker volume create appdata
docker volume ls
docker volume inspect appdata
```

Use:

```bash
docker run -d --name db -v appdata:/data alpine
```

## Bind mounts

Maps a specific host path into a container.

```bash
docker run -d   -v /home/ec2-user/app:/app   nginx
```

Useful for development, source code and configuration sharing.

## tmpfs

Stores data in memory.

```bash
docker run -d --tmpfs /tmp nginx
```

Useful for temporary data.

### Storage comparison

| Feature | Volume | Bind Mount | tmpfs |
|---|---|---|---|
| Docker managed | Yes | No | Yes |
| Persistent | Yes | Yes | No |
| Host disk | Yes | Yes | No |
| Memory backed | No | No | Yes |
| Common use | App/database data | Development/config | Temporary data |

# 11. Docker on AWS EC2

Example:

```bash
docker run -d --name web -p 8080:80 nginx
```

Flow:

```text
Internet
   |
EC2 Public IP:8080
   |
Security Group TCP 8080
   |
EC2
   |
Docker :8080
   |
Container :80
   |
Nginx
```

For Internet access, ensure:

1. Docker maps the host port.
2. The EC2 Security Group allows the port.
3. Network routing/NACLs permit the traffic.
4. The application is listening inside the container.

Test from EC2:

```bash
curl http://localhost:8080
```

# 12. Docker Port Range

TCP and UDP ports range from:

```text
0–65535
```

Common ranges:

```text
0–1023       Well-known
1024–49151   Registered
49152–65535  Dynamic/private
```

Docker host and container ports can differ:

```bash
docker run -d -p 91:80 nginx
```

Means:

```text
EC2 :91 ---> Container :80
```

Opening a port in an AWS Security Group does not make the port active. A process or Docker mapping must actually listen on it.

# 15. Docker Security Basics

Important practices:

- Do not run containers as root unnecessarily.
- Use trusted and minimal base images.
- Keep images updated.
- Do not hard-code passwords in Dockerfiles.
- Use secrets management.
- Scan images for vulnerabilities.
- Limit container capabilities.
- Avoid unnecessary host mounts.
- Be careful with Docker socket access.

Docker group membership is highly privileged because access to the Docker daemon can effectively provide root-level control of the host.

# 20. Scenario-Based Questions

### Scenario 1: Nginx is running but browser cannot connect

Check:

```bash
docker ps
docker port web
docker inspect web
```

Likely issue:

```bash
docker run -d -p 8080:80 nginx
```

For EC2, also allow TCP 8080 in the Security Group.

### Scenario 2: Container is deleted but data must remain

Use a volume:

```bash
docker volume create appdata
docker run -v appdata:/data ...
```

### Scenario 3: Two containers need to communicate

Use a user-defined bridge:

```bash
docker network create appnet
docker run -d --network appnet --name app ...
docker run -d --network appnet --name db ...
```

The application can use `db` as the hostname.

### Scenario 4: Containers on different Docker hosts need communication

Use an overlay network, typically with Docker Swarm.
