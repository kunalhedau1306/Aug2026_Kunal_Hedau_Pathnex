## 1. AWS Control Tower

AWS Control Tower helps organizations establish and govern a
multi-account AWS environment using automated account provisioning,
centralized governance, and controls.

Typical structure:

``` text
AWS Organization
├── Security Account
├── Log Archive Account
├── Network Account
├── Production Account
├── Development Account
└── Sandbox Account
```

### Why use Control Tower?

-   Standardize new AWS accounts
-   Apply governance controls
-   Establish a landing zone
-   Improve security and compliance
-   Provide centralized visibility

### Control Tower vs Organizations

  -----------------------------------------------------------------------
  AWS Organizations                   AWS Control Tower
  ----------------------------------- -----------------------------------
  Manages accounts and OUs            Helps establish and govern a
                                      multi-account environment

  SCPs                                Landing-zone automation and
                                      controls

  Consolidated billing                Account provisioning and governance

  Foundational service                Higher-level governance solution
  -----------------------------------------------------------------------

## 3. AWS Organizations

AWS Organizations centrally manages multiple AWS accounts.

### Key components

**Management account:** Controls the organization.

**Member account:** AWS account belonging to the organization.

**Organizational Unit (OU):** Logical grouping of accounts.

**Service Control Policy (SCP):** Defines the maximum permissions
available to principals in accounts/OUs. An SCP does **not** grant
permissions.

Example:

``` text
IAM Policy: Allow EC2 actions
       |
       v
SCP: Deny selected regions
       |
       v
Effective permissions are restricted
```

Useful CLI commands:

``` bash
aws organizations describe-organization
aws organizations list-accounts
aws organizations list-roots
```

## 4. AWS Systems Manager Session Manager

Session Manager provides managed shell access to EC2 instances without
requiring inbound SSH.

Traditional approach:

``` text
Administrator --> SSH/22 --> Bastion --> Private EC2
```

Session Manager:

``` text
Administrator
      |
      v
AWS Systems Manager
      |
      v
Private EC2
```

### Benefits

-   No inbound port 22 required
-   No bastion host required in many architectures
-   IAM-based authorization
-   Works with private instances when required Systems Manager
    connectivity exists
-   Session activity can be integrated with logging/auditing

Common requirement: - SSM Agent - Appropriate IAM instance role,
commonly including `AmazonSSMManagedInstanceCore` - Connectivity to
Systems Manager endpoints

CLI:

``` bash
aws ssm describe-instance-information
aws ssm start-session --target <instance-id>
```

## 5. Amazon Route 53

Route 53 is AWS's highly available DNS and domain-management service.

### Common record types

**A:** hostname to IPv4 address.

**AAAA:** hostname to IPv6 address.

**CNAME:** hostname to another hostname.

**Alias:** AWS-specific routing to supported AWS resources such as ALB
and CloudFront.

Example:

``` text
www.example.com
       |
       v
    Route 53
       |
       v
Application Load Balancer
       |
       v
      EC2
```

### Routing policies

-   Simple
-   Weighted
-   Latency-based
-   Failover
-   Geolocation
-   Geoproximity
-   IP-based (where applicable)

Example weighted routing:

``` text
90% --> Production
10% --> New Version
```

Useful CLI:

``` bash
aws route53 list-hosted-zones
aws route53 list-resource-record-sets --hosted-zone-id <zone-id>
```

## 6. AWS CloudTrail

CloudTrail records AWS API activity and provides an audit trail.

Memory trick:

> CloudTrail answers: **Who did what, when, and from where?**

Events can contain: - Event name - User/role identity - Time - Source
IP - AWS Region - Request parameters - Resource information

Examples:

``` text
RunInstances
TerminateInstances
StopInstances
CreateBucket
AssumeRole
```

CLI:

``` bash
aws cloudtrail describe-trails
aws cloudtrail lookup-events
```

### CloudTrail example

If an EC2 instance was unexpectedly terminated, CloudTrail can help
identify the API event and the identity that made the request.

## 7. Amazon CloudWatch

CloudWatch provides monitoring and observability.

It works with: - Metrics - Logs - Alarms - Dashboards - Events and
related integrations

Example:

``` text
EC2 CPU > 80%
       |
       v
CloudWatch Alarm
       |
       v
Auto Scaling action
```

Common EC2 metrics include: - CPUUtilization - NetworkIn - NetworkOut -
StatusCheckFailed

CLI:

``` bash
aws cloudwatch list-metrics
aws cloudwatch describe-alarms
```

### CloudTrail vs CloudWatch

  CloudTrail            CloudWatch
  --------------------- -------------------------------
  Audit/API activity    Monitoring/observability
  Who did what?         How is the system performing?
  API events            Metrics and logs
  Security/compliance   Operations/performance

## 8. AWS Auto Scaling

Auto Scaling automatically adjusts capacity according to demand.

``` text
High demand
    |
    v
Scale Out
    |
More EC2 instances

Low demand
    |
    v
Scale In
    |
Fewer EC2 instances
```

### EC2 Auto Scaling Group

An ASG maintains a fleet of EC2 instances.

Important settings: - Minimum capacity - Desired capacity - Maximum
capacity

Example:

``` text
Minimum = 2
Desired = 3
Maximum = 6
```

If demand increases, the ASG can launch instances up to the maximum.

If demand decreases, it can terminate instances while maintaining at
least the minimum.

------------------------------------------------------------------------

## 9. Horizontal vs Vertical Scaling

### Horizontal scaling

Add or remove instances.

``` text
EC2-1
EC2-2
EC2-3
```

Called: - Scale out - Scale in

### Vertical scaling

Increase or decrease the capacity of one machine.

``` text
t3.small
   |
   v
t3.large
```

Called: - Scale up - Scale down

  Horizontal                 Vertical
  -------------------------- ----------------------------------
  Add/remove instances       Change instance size
  Scale out/in               Scale up/down
  Common with ASGs           Usually explicit capacity change
  Can improve availability   Larger single machine

------------------------------------------------------------------------

## 10. Auto Scaling Policies

### Target Tracking

Maintain a target metric.

Example:

``` text
Target CPU = 50%
```

The service adjusts capacity to move toward the target.

### Step Scaling

Different thresholds cause different scaling actions.

``` text
CPU 60-70%  -> +1
CPU 70-80%  -> +2
CPU >80%    -> +3
```

### Scheduled Scaling

Useful when demand is predictable.

``` text
08:00 -> Scale out
20:00 -> Scale in
```

### Predictive Scaling

Uses historical patterns to forecast demand and adjust capacity.

## 11. Auto Scaling + Load Balancer

Common architecture:

``` text
                 Internet
                    |
                 Route 53
                    |
             Load Balancer
                    |
       +------------+------------+
       |            |            |
      EC2          EC2          EC2
       +------------+------------+
                    |
             Auto Scaling Group
```

The load balancer distributes traffic. The Auto Scaling Group adjusts
the number of EC2 instances.

## 12. Auto Scaling Health Checks

If an instance becomes unhealthy:

``` text
ASG
 |
 v
Detect unhealthy instance
 |
 v
Terminate/replace
 |
 v
Launch replacement
```

This helps maintain desired capacity and application availability.
