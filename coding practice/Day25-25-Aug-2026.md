**Audience:** Technical Application Management / DevOps learners  
**Note:** “Promotheus” is commonly written as **Prometheus**.

## 1. DevOps monitoring fundamentals

### 1.1 Purpose of monitoring

Monitoring provides continuous visibility into the health, performance, capacity, and availability of infrastructure and applications. Its purpose is not merely to create alerts; it should help teams detect issues early, assess user impact, troubleshoot quickly, and improve reliability over time.

| Monitoring area | Key question | Examples |
|---|---|---|
| Availability | Is the service reachable? | HTTPS endpoint, DNS resolution, TCP port, uptime |
| Infrastructure | Is the host healthy? | CPU, memory, disk, file systems, network errors |
| Application | Is the application behaving correctly? | Request rate, errors, latency, JVM heap, thread pools |
| Database | Can it serve workload safely? | Sessions, tablespaces, response time, replication lag |
| Capacity | Will a resource run out? | Disk growth, CPU saturation, connection pool use |
| Security / operations | Are abnormal events occurring? | Certificate expiry, failed logins, backup failures |

### 1.2 Observability signals

The three main observability signals are:

- **Metrics:** Numeric values measured over time, such as CPU utilisation, HTTP request duration, or free disk bytes.
- **Logs:** Detailed, discrete event records, such as WebLogic error logs or Apache access logs.
- **Traces:** A request-level journey across services, useful for distributed applications.

Prometheus is primarily a **metrics** platform. Grafana visualises metrics and can also visualise logs and traces when connected to appropriate data sources.

### 1.3 The four golden signals

| Signal | Meaning | Example |
|---|---|---|
| Latency | How long a request takes | 95th percentile API response time > 2 seconds |
| Traffic | Demand placed on the system | Requests/second to a web service |
| Errors | Failed requests or operations | HTTP 5xx rate, failed batch jobs |
| Saturation | How close a resource is to its limit | Disk usage, JVM heap, DB connection pool usage |

### 1.4 Monitoring versus alerting

- **Monitoring** collects and displays data for investigation and trend analysis.
- **Alerting** notifies a responsible team when a measured condition requires action.

An alert should be actionable. “CPU is 85% for five minutes” may be useful, but “Customer portal is unavailable” is usually more urgent and meaningful. Alert on symptoms and user impact first; use resource alerts as early warnings.

## 2. Prometheus overview

### 2.1 What Prometheus is

Prometheus is an open-source monitoring and alerting system designed around a time-series database. It collects metrics by calling HTTP endpoints, stores the data locally, evaluates rules, and exposes a query language named **PromQL**.

Prometheus normally uses a **pull model**: it periodically scrapes an HTTP `/metrics` endpoint from each target. The official getting-started guide uses a default scrape interval of 15 seconds and shows Prometheus scraping its own HTTP metrics endpoint. [Prometheus documentation](https://prometheus.io/docs/prometheus/latest/getting_started/)

### 2.2 Prometheus architecture

```text
Linux / application targets
  └─ Exporters expose /metrics
          ↓  HTTP scrape
Prometheus server ──> Local time-series database
      │
      ├─ PromQL queries ──> Grafana dashboards
      │
      └─ Alert rules ──> Alertmanager ──> Email / Teams / PagerDuty
```

| Component | Responsibility |
|---|---|
| **Prometheus server** | Scrapes targets, stores time-series data, runs PromQL queries and rules. |
| **Target** | A service or host from which metrics are collected. |
| **Exporter** | Converts system/application data into Prometheus metric format. |
| **Node Exporter** | Standard exporter for Linux host metrics: CPU, memory, filesystem, network, etc. |
| **Alertmanager** | Groups, deduplicates, silences, routes, and delivers alerts. |
| **Grafana** | Visualises Prometheus data in dashboards and supports alerting. |
| **Service discovery** | Dynamically finds targets, e.g., Kubernetes, EC2, Consul, or file-based discovery. |

### 2.3 Data model

Prometheus stores a metric as a **time series**, identified by:

```text
metric_name{label_name="label_value", ...} timestamp value
```

Example:

```text
node_filesystem_avail_bytes{instance="app01:9100", mountpoint="/usr", job="linux"} 17179869184
```

This represents 16 GiB available on `/usr` of `app01`.

### 2.4 Metric types

| Type | Behaviour | Example | PromQL approach |
|---|---|---|---|
| **Counter** | Only increases, except when the process restarts. | `http_requests_total` | Calculate change per second using `rate()`. |
| **Gauge** | Can increase or decrease. | `node_memory_MemAvailable_bytes` | Query the current value directly. |
| **Histogram** | Observations in buckets plus count and sum. | HTTP duration buckets | Use `histogram_quantile()` for percentiles. |
| **Summary** | Client-calculated quantiles plus count and sum. | Request duration summary | Use reported quantiles carefully; not aggregatable across instances. |

### 2.5 Labels and cardinality

Labels make metrics filterable and groupable. Useful stable labels include:

```text
environment="acc"     customer="anl"     service="portal"     role="weblogic"
```

Avoid high-cardinality labels—labels that create a large number of unique combinations. Do **not** use user IDs, request IDs, session IDs, random UUIDs, full URLs with changing parameters, or timestamps as labels. Such data belongs in logs/traces, not metric labels.

## 3. Prometheus configuration and PromQL

### 3.1 Basic `prometheus.yml`

```yaml
global:
  scrape_interval: 15s
  evaluation_interval: 15s
  external_labels:
    environment: acc
    customer: anl

rule_files:
  - /etc/prometheus/rules/*.yml

scrape_configs:
  - job_name: prometheus
    static_configs:
      - targets: ['localhost:9090']

  - job_name: linux
    static_configs:
      - targets:
          - 'app01.example.internal:9100'
          - 'db01.example.internal:9100'
          - 'rpx01.example.internal:9100'

  - job_name: application
    metrics_path: /metrics
    static_configs:
      - targets: ['app01.example.internal:8080']
```

Important fields:

- `scrape_interval`: frequency at which Prometheus requests metrics.
- `evaluation_interval`: frequency for recording and alert rules.
- `job_name`: becomes the `job` label.
- `static_configs`: fixed target list; suitable for a small lab or stable estate.
- `metrics_path`: defaults to `/metrics` but can be changed for an exporter/application endpoint.
- `external_labels`: identifies where a Prometheus instance is running when using federation, remote write, or Alertmanager.

### 3.2 Check configuration before reload

```bash
promtool check config /etc/prometheus/prometheus.yml
promtool check rules /etc/prometheus/rules/*.yml
```

Only reload a verified configuration. A running Prometheus instance can reload configuration without a full restart when started with lifecycle administration enabled, or through a managed service/systemd reload approach.

### 3.3 Useful PromQL queries

| Objective | PromQL |
|---|---|
| Target availability | `up` |
| Show targets that are down | `up == 0` |
| CPU busy percentage by host | `100 - (avg by (instance) (rate(node_cpu_seconds_total{mode="idle"}[5m])) * 100)` |
| Memory used percentage | `100 * (1 - node_memory_MemAvailable_bytes / node_memory_MemTotal_bytes)` |
| Filesystem used percentage for `/usr` | `100 * (1 - node_filesystem_avail_bytes{mountpoint="/usr",fstype!~"tmpfs|overlay"} / node_filesystem_size_bytes{mountpoint="/usr",fstype!~"tmpfs|overlay"})` |
| Filesystem free GiB for `/usr` | `node_filesystem_avail_bytes{mountpoint="/usr",fstype!~"tmpfs|overlay"} / 1024 / 1024 / 1024` |
| Network receive bytes/sec | `rate(node_network_receive_bytes_total[5m])` |
| HTTP 5xx percentage | `100 * sum(rate(http_requests_total{code=~"5.."}[5m])) / sum(rate(http_requests_total[5m]))` |
| HTTP p95 latency from histogram | `histogram_quantile(0.95, sum by (le) (rate(http_request_duration_seconds_bucket[5m])))` |

### 3.4 PromQL principles

- Use `rate(counter[window])` for counters; use a range that is comfortably larger than the scrape interval.
- Use `sum by (label)` or `avg by (label)` intentionally; aggregation without a `by` clause removes all labels.
- Use exact label matches where possible; regular expressions are more expensive and harder to maintain.
- Always validate an alert query in the Prometheus expression browser before deploying it.
- Use recording rules for expensive or repeated calculations.

## 4. Exporters

### 4.1 Common exporters

| Exporter | Monitors | Typical endpoint |
|---|---|---|
| Node Exporter | Linux operating system resources | `http://host:9100/metrics` |
| Windows Exporter | Windows OS resources and services | `http://host:9182/metrics` |
| Blackbox Exporter | External HTTP/HTTPS, TCP, DNS, ICMP probes | `http://exporter:9115/probe` |
| JMX Exporter | JVM/WebLogic application metrics | Java agent or standalone exporter |
| Oracle DB exporter | Oracle database metrics | Exporter-specific HTTP endpoint |
| Nginx/Apache exporter | Web server status metrics | Exporter-specific HTTP endpoint |
| SNMP exporter | Network devices and appliances | Exporter endpoint after SNMP polling |

### 4.2 Pull versus push

The normal model is **Prometheus pulls metrics** from targets. This gives the monitoring platform control over collection and lets it identify unreachable targets through the `up` metric.

For short-lived batch jobs, a **Pushgateway** may be appropriate: the job pushes its final status/metric, and Prometheus scrapes the Pushgateway. Do not use it as a general replacement for exporters because stale data can remain after a job or host disappears.

## 5. Alerting and Alertmanager

### 5.1 Alert rule example

Create `/etc/prometheus/rules/host-alerts.yml`:

```yaml
groups:
  - name: host-health
    rules:
      - alert: HostDown
        expr: up{job="linux"} == 0
        for: 5m
        labels:
          severity: critical
        annotations:
          summary: "Linux host {{ $labels.instance }} is unreachable"
          description: "Prometheus has been unable to scrape {{ $labels.instance }} for 5 minutes."

      - alert: UsrFilesystemLow
        expr: |
          node_filesystem_avail_bytes{mountpoint="/usr",fstype!~"tmpfs|overlay"}
          / node_filesystem_size_bytes{mountpoint="/usr",fstype!~"tmpfs|overlay"} < 0.15
        for: 15m
        labels:
          severity: warning
        annotations:
          summary: "/usr free space is below 15% on {{ $labels.instance }}"
          description: "Investigate capacity or extend the LVM filesystem before service impact."
```

The `for` duration prevents a transient failure from creating a notification immediately. Choose the duration based on business impact and known behaviour.

### 5.2 Alert lifecycle

```text
Metric crosses threshold
        ↓
Prometheus evaluates rule
        ↓
Pending for configured “for” duration
        ↓
Firing alert sent to Alertmanager
        ↓
Alertmanager groups/routes/deduplicates
        ↓
Email, Teams, PagerDuty, or another receiver
```

### 5.3 Alert quality rules

- Include a clear summary, impact, affected target, and first troubleshooting action.
- Add labels such as `severity`, `team`, `service`, `environment`, and `runbook_url` where governance permits.
- Avoid alerts for every metric. Alert only when a human action is useful.
- Group related alerts to avoid notification storms.
- Use silences during approved maintenance and retain a change/Jira reference.
- Review noisy alerts regularly; either improve the condition or remove it.

## 6. Grafana overview

### 6.1 What Grafana is

Grafana is a visualisation and observability platform. It connects to a data source such as Prometheus and displays results in dashboards, panels, variables, alerts, and annotations.

Grafana supports RHEL/Fedora installation paths and lists 512 MB RAM and one CPU core as minimum resources; for a small internal production deployment, plan more headroom and separately size Prometheus/data sources. [Grafana installation documentation](https://grafana.com/docs/grafana/latest/setup-grafana/installation/)

### 6.2 Grafana concepts

| Concept | Purpose |
|---|---|
| Data source | Connection configuration to Prometheus, Loki, PostgreSQL, etc. |
| Dashboard | Collection of visual panels focused on a service or domain. |
| Panel | A graph, gauge, table, stat, heatmap, or other visualisation. |
| Query | PromQL expression that returns panel data. |
| Variable | Dynamic filter, e.g., environment, instance, job, customer. |
| Annotation | Event marker on a graph, e.g., release, maintenance, or incident. |
| Folder | Organises dashboards and controls dashboard permissions. |
| Alert rule | Evaluates a query and sends a notification through a configured contact point. |

### 6.3 Recommended dashboard hierarchy

```text
Platform dashboards
  ├─ Infrastructure overview
  ├─ Linux host detail
  ├─ Reverse proxy / Apache detail
  ├─ WebLogic / JVM detail
  ├─ Oracle database detail
  └─ Application / API service detail

Business/service dashboards
  ├─ Customer environment overview (ACC / PRE / PRD)
  └─ Release / deployment health
```

### 6.4 Useful panel types

| Panel type | Best use |
|---|---|
| Stat | Current availability, active alerts, latest deployment version. |
| Time series | CPU, memory, latency, error rate, response rate trends. |
| Gauge / bar gauge | Capacity percentage or threshold status. |
| Table | Target inventory, alert list, top consumers, filesystem list. |
| Heatmap | Latency distributions or dense event data. |
| State timeline | Uptime, maintenance periods, job/service states. |

## 7. Practical lab: Prometheus, Node Exporter, and Grafana on EC2

### 7.1 Lab objective

Build a small monitoring stack that:

1. Runs Prometheus and Grafana on one monitoring EC2 instance.
2. Runs Node Exporter on one or more monitored Linux EC2 instances.
3. Shows host availability, CPU, memory, and `/usr` filesystem capacity in Grafana.
4. Fires an alert when a monitored host is unavailable or `/usr` capacity is low.

### 7.2 Lab topology

```text
Admin browser ─HTTPS─> Grafana EC2 (3000 via reverse proxy / 443)
                              │
                              └─ Prometheus (9090, internal only)
                                      │
                                      ├─ Node Exporter app01 (9100)
                                      └─ Node Exporter db01  (9100)
```

### 7.3 Security group design

| Destination | Port | Allowed source | Purpose |
|---|---:|---|---|
| Grafana | 443 | Administrator VPN / approved corporate range | User access through HTTPS. |
| Grafana direct UI | 3000 | Monitoring host or admin range only | Prefer not to expose directly. |
| Prometheus | 9090 | Monitoring subnet only | Administrative/query access; do not publish publicly. |
| Node Exporter | 9100 | Prometheus security group only | Prometheus scrape traffic. |
| SSH | 22 | Bastion / management range only | Administration; SSM is preferable if available. |

Never expose ports 9100, 9090, or 3000 directly to the public internet.

### 7.4 Install Node Exporter using containers (lab method)

On each monitored Linux host, install Docker/Podman according to the OS standard, then run Node Exporter. Example with Docker:

```bash
sudo docker run -d \
  --name node-exporter \
  --restart unless-stopped \
  --network host \
  --pid host \
  -v /:/host:ro,rslave \
  quay.io/prometheus/node-exporter:latest \
  --path.rootfs=/host
```

Verify locally:

```bash
curl -fsS http://localhost:9100/metrics | head
```

For production, pin a tested image version or use an approved package/service deployment managed through Puppet or Ansible. Avoid relying on `latest`.

### 7.5 Create the Prometheus configuration

On the monitoring instance, create `prometheus.yml`:

```yaml
global:
  scrape_interval: 15s
  evaluation_interval: 15s

rule_files:
  - /etc/prometheus/rules/*.yml

scrape_configs:
  - job_name: prometheus
    static_configs:
      - targets: ['prometheus:9090']

  - job_name: linux
    static_configs:
      - targets:
          - 'app01.example.internal:9100'
          - 'db01.example.internal:9100'
        labels:
          environment: acc
          customer: anl
```

Replace the hostnames with the private DNS names or private IP addresses reachable from Prometheus.

### 7.6 Run Prometheus and Grafana with Docker Compose (lab method)

Create `compose.yml`:

```yaml
services:
  prometheus:
    image: prom/prometheus:<TESTED_VERSION>
    container_name: prometheus
    restart: unless-stopped
    ports:
      - "127.0.0.1:9090:9090"
    volumes:
      - ./prometheus.yml:/etc/prometheus/prometheus.yml:ro
      - ./rules:/etc/prometheus/rules:ro
      - prometheus_data:/prometheus
    command:
      - --config.file=/etc/prometheus/prometheus.yml
      - --storage.tsdb.path=/prometheus
      - --web.enable-lifecycle

  grafana:
    image: grafana/grafana:<TESTED_VERSION>
    container_name: grafana
    restart: unless-stopped
    ports:
      - "127.0.0.1:3000:3000"
    environment:
      GF_SECURITY_ADMIN_USER: admin
      GF_SECURITY_ADMIN_PASSWORD: CHANGE_THIS_IMMEDIATELY
      GF_USERS_ALLOW_SIGN_UP: "false"
    volumes:
      - grafana_data:/var/lib/grafana

volumes:
  prometheus_data:
  grafana_data:
```

Start the stack:

```bash
docker compose up -d
docker compose ps
docker compose logs -f prometheus
```

The example pins versions deliberately. Before a real deployment, select currently supported versions, scan the images, record the versions, and validate upgrades in a non-production environment.

### 7.7 Verify targets

1. Reach Prometheus through an approved administrative path.
2. Open **Status → Targets**.
3. Confirm that the Prometheus and Linux targets show `UP`.
4. Run the following in the Prometheus query page:

```promql
up
```

If a target is `DOWN`, test in this order:

```bash
# From the Prometheus host
curl -v http://app01.example.internal:9100/metrics

# On the target host
systemctl status node_exporter   # package/service installation
docker ps                        # container installation
ss -lntp | grep 9100
```

Then check DNS, security groups/firewalls, exporter process, TLS/authentication settings, and the target definition.

### 7.8 Configure Grafana

1. Access Grafana through the approved HTTPS route.
2. Change the initial administrator password and create named user accounts or configure SSO.
3. Go to **Connections → Data sources → Add data source**.
4. Select **Prometheus**.
5. Set the URL to `http://prometheus:9090` when both containers are on the same Compose network; use the correct internal Prometheus URL for separate hosts.
6. Select **Save & test**.
7. Create a folder named `Infrastructure` and a dashboard named `Linux Host Overview`.

### 7.9 Build four dashboard panels

| Panel | Visualisation | Query | Suggested threshold |
|---|---|---|---|
| Target status | Stat | `up{job="linux"}` | 1 = green; 0 = red |
| CPU used % | Time series | `100 - (avg by (instance) (rate(node_cpu_seconds_total{mode="idle"}[5m])) * 100)` | Warning 80%, critical 95% |
| Memory used % | Time series | `100 * (1 - node_memory_MemAvailable_bytes / node_memory_MemTotal_bytes)` | Warning 80%, critical 90% |
| `/usr` free GiB | Time series | `node_filesystem_avail_bytes{mountpoint="/usr",fstype!~"tmpfs|overlay"} / 1024 / 1024 / 1024` | Alert based on capacity/growth rate |

Create an `instance` dashboard variable to let users filter a dashboard:

```promql
label_values(node_uname_info{job="linux"}, instance)
```

Use it in panel selectors as `instance=~"$instance"`.

### 7.10 Add alert rules

Create `rules/host-alerts.yml` from the example in section 5.1, then validate/reload Prometheus:

```bash
docker exec prometheus promtool check rules /etc/prometheus/rules/host-alerts.yml
curl -X POST http://127.0.0.1:9090/-/reload
```

In a real implementation, deploy rules via Git + CI/CD, validate them with `promtool`, and use an approved configuration-management workflow—not manual edits on the monitoring server.

## 8. Practical use for a WebLogic / Oracle application stack

| Layer | Metrics to monitor | Example response |
|---|---|---|
| RPX / Apache | HTTP request rate, 4xx/5xx rate, worker utilisation, response time, TLS certificate expiry | Investigate routing, backend availability, error logs, and certificate renewal. |
| WebLogic / JVM | Managed-server state, heap use, GC time, thread pool, JDBC pool, stuck threads, deployment health | Check server state, heap/GC pattern, JDBC targets, and application logs. |
| Oracle DB | Availability, sessions, tablespace free space, blocking sessions, response time, Data Guard transport/apply lag | Check database health, capacity, listener, and Data Guard status. |
| Linux | CPU, memory, `/usr`/data filesystem, inode use, processes, network errors | Extend LVM capacity, resolve process/resource pressure, or investigate connectivity. |
| Synthetic user path | HTTPS availability and expected response from portal/API endpoint | Confirm customer impact, DNS/LB/RPX path, and backend application state. |

For LeanApps Life-style environments, start with host availability, disk capacity, reverse proxy health, WebLogic/JVM health, Oracle availability/capacity, and a customer-facing endpoint. Build dashboards around the service rather than creating disconnected dashboards for each tool.

## 9. Production design and security checklist

- Use DNS names, TLS, authenticated access, and SSO/role-based permissions for Grafana.
- Keep Prometheus and exporter ports internal; segment scrape traffic through security groups/firewall rules.
- Separate viewer, editor, and administrator permissions in Grafana.
- Store Grafana secrets, database credentials, and alert-channel webhooks in an approved secret store.
- Protect sensitive labels. Never put customer data, tokens, identifiers, or request payloads in metrics labels.
- Retain metrics according to capacity, compliance, and troubleshooting needs; local Prometheus storage alone may not satisfy long retention or HA requirements.
- Use external long-term storage/remote write only after documenting data ownership, cost, retention, and recovery requirements.
- Run multiple Prometheus/Alertmanager instances or use a managed design when monitoring availability is business-critical.
- Back up Grafana configuration, dashboards, provisioning code, and the data required to restore the service.
- Manage dashboards, alert rules, and Prometheus configuration as code in Git; review and test changes through CI/CD.
- Add release and maintenance annotations to dashboards to correlate incidents with changes.
- Review dashboard query load and refresh intervals—many panels refreshing every few seconds can overload Prometheus and Grafana.

## 10. Troubleshooting quick reference

| Symptom | Likely checks |
|---|---|
| Target is DOWN | Exporter running, port listening, DNS, firewall/security group, Prometheus target configuration. |
| No data in Grafana | Prometheus data-source URL, dashboard time range, PromQL query, target state, Grafana permissions. |
| `No data` after a deployment | Check new labels/metric names, scrape path, service discovery, and application metrics endpoint. |
| High Prometheus memory/disk use | Cardinality, scrape interval, retention period, target count, expensive rules, local TSDB health. |
| No alert notification | Rule state, `for` duration, Alertmanager endpoint, route/receiver, silence/inhibition, contact-point configuration. |
| Grafana dashboard slow | Too many panels, short refresh period, unbounded PromQL query, high-cardinality metrics, datasource performance. |
