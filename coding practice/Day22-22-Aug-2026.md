## 1. What is Ansible?

Ansible is an automation tool used for configuration management, application deployment, infrastructure automation, server provisioning, software installation, service management, orchestration, security and patching automation.

Ansible is generally **agentless**. For Linux/Unix managed nodes, it commonly connects through SSH and executes modules remotely.

```text
                    CONTROL NODE
                 Ansible installed
                         |
             +-----------+-----------+
             |           |           |
            SSH         SSH         SSH
             |           |           |
             v           v           v
          Server-1    Server-2    Server-3
          Web         App         DB
```

The machine from which Ansible commands are executed is the **control node**. Target machines are **managed nodes**.

## 3. Inventory

An inventory contains the hosts that Ansible manages.

```ini
[webservers]
web1
web2

[appservers]
app1
app2

[dbservers]
db1
```

Inventory can contain hostnames, IP addresses, groups, host variables and connection information.

Example:

```ini
[webservers]
192.168.1.10
192.168.1.11

[dbservers]
192.168.1.20
```

### Test connectivity

```bash
ansible all -i inventory -m ping
```

The Ansible `ping` module is not ICMP ping. It verifies Ansible connectivity and module execution on the managed node.

## 4. Playbook

A playbook is an automation blueprint written in YAML.

```text
Which servers?
      ↓
What tasks?
      ↓
Which modules?
      ↓
What final state?
```

Example:

```yaml
---
- name: Install Nginx
  hosts: webservers
  become: true

  tasks:
    - name: Install Nginx
      ansible.builtin.package:
        name: nginx
        state: present

    - name: Start Nginx
      ansible.builtin.service:
        name: nginx
        state: started
        enabled: true
```

Run:

```bash
ansible-playbook -i inventory nginx.yml
```

## 5. Play vs Playbook vs Task

### Playbook

A YAML file containing one or more plays.

### Play

Defines target hosts, variables, tasks, roles and handlers.

```yaml
- name: Configure web servers
  hosts: webservers
  tasks:
    ...
```

### Task

An individual action.

```yaml
- name: Install nginx
  ansible.builtin.package:
    name: nginx
    state: present
```

## 7. Roles

A role provides a reusable structure for Ansible automation.

```text
roles/
└── nginx/
    ├── defaults/main.yml
    ├── handlers/main.yml
    ├── tasks/main.yml
    ├── templates/
    ├── files/
    ├── vars/main.yml
    └── meta/main.yml
```

Roles organize tasks, variables, handlers, templates, files and metadata.

## 8. Why Use Roles?

Instead of maintaining separate automation for every server:

```text
nginx-role
     |
     +-- install nginx
     +-- configure nginx
     +-- copy configuration
     +-- start service
     +-- enable service
```

Benefits:

- Reusability
- Standardization
- Maintainability
- Easier testing
- Better organization

Detailed workflow:

```text

        ↓

        ↓

        ↓

```

## 12. Nginx Installation

Identify the OS:

```bash
cat /etc/os-release
```

On RHEL/Amazon Linux systems where `dnf` is available:

```bash
sudo dnf install nginx -y
nginx -v
sudo systemctl start nginx
sudo systemctl enable nginx
sudo systemctl status nginx
curl http://localhost
```

### Ansible Playbook

```yaml
---
- name: Install and start Nginx
  hosts: webservers
  become: true

  tasks:
    - name: Install Nginx
      ansible.builtin.dnf:
        name: nginx
        state: present

    - name: Start and enable Nginx
      ansible.builtin.service:
        name: nginx
        state: started
        enabled: true
```

Run:

```bash
ansible-playbook -i inventory nginx.yml
```

## 14. Nginx vs Apache Service Names

| Application | Package | Service |
|---|---|---|
| Nginx | `nginx` | `nginx` |
| Apache on RHEL | `httpd` | `httpd` |
| Apache on Debian/Ubuntu | `apache2` | `apache2` |

On RHEL/Amazon Linux:

```bash
systemctl start httpd
```

not:

```bash

```

## 17. Common Problem – Port 80 Not Listening

Check:

```bash
ss -lntp | grep :80
```

If nothing appears, the web server is not listening on port 80.

Check:

```bash
systemctl status nginx
systemctl status httpd
```

Then inspect logs:

```bash
journalctl -u nginx
journalctl -u httpd
```

## 18. Common Problem – Port Already in Use

If Nginx reports:

```text
Address already in use
```

check:

```bash
ss -lntp | grep :80
```

If Apache already owns port 80, Nginx cannot also bind to the same IP/port combination.

Solutions:

- Stop Apache
- Change Nginx's listening port
- Configure a reverse proxy

## 19. Nginx and Apache Together

Example architecture:

```text
Internet
   |
   v
Nginx :80
   |
   v
Apache :8080
   |
   v
Application
```

Nginx can listen on port 80 and proxy requests to Apache on 8080.

## 20. Ansible Playbook to Install Both

```yaml
---
- name: Install Nginx and Apache
  hosts: webservers
  become: true

  tasks:
    - name: Install Nginx
      ansible.builtin.dnf:
        name: nginx
        state: present

    - name: Install Apache
      ansible.builtin.dnf:
        name: httpd
        state: present

    - name: Start Nginx
      ansible.builtin.service:
        name: nginx
        state: started
        enabled: true

    - name: Start Apache
      ansible.builtin.service:
        name: httpd
        state: started
        enabled: true
```

**Important:** This may fail if both services attempt to bind to port 80. Configure different ports first if both need to run simultaneously.

## 23. Idempotency

Idempotency means repeated execution converges on the desired state without unnecessary changes.

Example:

```yaml
- name: Install nginx
  ansible.builtin.dnf:
    name: nginx
    state: present
```

First execution may report:

```text
changed=1
```

A subsequent execution should normally report no change if Nginx is already installed.

Similarly:

```yaml
state: started
```

means ensure the service is running.

## 24. Handlers

Handlers are useful when a configuration change should trigger a restart.

```yaml
---
- name: Configure Nginx
  hosts: webservers
  become: true

  tasks:
    - name: Copy Nginx configuration
      ansible.builtin.copy:
        src: nginx.conf
        dest: /etc/nginx/nginx.conf
      notify:
        - Restart Nginx

  handlers:
    - name: Restart Nginx
      ansible.builtin.service:
        name: nginx
        state: restarted
```

The handler runs when the notified task reports a change.

## 26. Key Interview Questions

### What is Ansible?

An agentless automation and configuration-management tool.

### What is an inventory?

A source defining managed nodes and their groups/variables.

### What is a playbook?

A YAML automation blueprint containing plays and tasks.

### What is a module?

A reusable unit that performs a specific operation on a managed node.

### What is a role?

A reusable, standardized structure for organizing Ansible automation.

### What is idempotency?

Running automation repeatedly should not make unnecessary changes once the desired state has been reached.

### What is `become: true`?

It enables privilege escalation, commonly to root.

### What is a handler?

A task that runs when notified by another task that changed something.

### How does Ansible communicate with Linux servers?

Typically through SSH.

### Does Ansible require an agent on Linux managed nodes?

Normally no. Ansible generally uses SSH and executes modules remotely.

### What is the difference between `command` and `shell`?

`command` executes commands without a shell; `shell` executes through a shell and supports shell features such as pipes and redirection. Prefer dedicated modules when one exists.

### What is the difference between `ansible` and `ansible-playbook`?

```text
ansible
    ↓
Ad-hoc commands

ansible-playbook
    ↓
Execute YAML playbooks
```
