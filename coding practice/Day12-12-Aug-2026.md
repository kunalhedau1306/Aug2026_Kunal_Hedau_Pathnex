## 1. What is Kubernetes?

Kubernetes (K8s) is an open-source **container orchestration platform**. It automates the deployment, scaling, networking, self-healing, and management of containerized applications.

### Simple definition

> Kubernetes is a platform that automatically manages containerized applications across a cluster of machines.

### Why do we need it?

If we run one container, Docker may be enough. But with many containers and servers, we need automation for:

- Scheduling containers
- Scaling applications
- Restarting failed workloads
- Load balancing
- Service discovery
- Rolling updates
- Rollbacks
- Configuration and secrets
- Maintaining desired state

# 3. Kubernetes Cluster

A Kubernetes **cluster** is a group of machines working together to run containerized applications.

```text
Kubernetes Cluster
 |
 +-- Control Plane
 |
 +-- Worker Node 1
 |
 +-- Worker Node 2
 |
 +-- Worker Node 3
```

A cluster has two major logical parts:

1. Control Plane
2. Worker Nodes

# 5. Control Plane

The Control Plane manages the Kubernetes cluster.

Main components:

```text
Control Plane
 |
 +-- kube-apiserver
 +-- etcd
 +-- kube-scheduler
 +-- kube-controller-manager
```

Depending on the environment, a cloud controller manager may also be present.

The Control Plane answers questions such as:

- Where should a Pod run?
- How many replicas should exist?
- Is a workload healthy?
- Has the desired configuration changed?
- What action is required to make current state match desired state?

# 6. kube-apiserver

The **kube-apiserver** is the main API entry point for Kubernetes.

For example:

```bash
kubectl get pods
```

The request goes through the API Server.

```text
kubectl
   |
   v
kube-apiserver
   |
   +-- etcd
   +-- Scheduler
   +-- Controllers
   +-- Worker Nodes
```

The API Server handles functions such as:

- API requests
- Authentication
- Authorization
- Validation
- Admission processing
- Updating cluster state

### Society analogy

The API Server is the **society management office**. Residents normally submit requests to the office rather than directly changing the society records.

---

# 7. etcd

**etcd** is a distributed key-value store used by Kubernetes to store cluster state.

It stores important information such as:

- Cluster configuration
- Pods
- Deployments
- Services
- Nodes
- ConfigMaps
- Secrets
- Desired state

Think of etcd as the **official society register/database**.

Example:

```text
etcd
 |
 +-- Desired replicas = 3
 +-- Pods
 +-- Services
 +-- Nodes
 +-- Configuration
```

### Important

etcd is critical to the cluster. Losing its data can seriously affect the Kubernetes control plane state, so backups are important.

---

# 8. kube-scheduler

The **kube-scheduler** decides which worker node should run a newly scheduled Pod.

```text
New Pod
   |
   v
Scheduler
   |
   +-- Node 1
   +-- Node 2
   +-- Node 3
```

The scheduler considers factors such as:

- CPU and memory availability
- Resource requests
- Node selectors
- Affinity/anti-affinity
- Taints and tolerations
- Scheduling constraints

### Society analogy

A new family wants a flat. The manager checks available and suitable flats and assigns one.

---

# 9. kube-controller-manager

Controllers continuously compare:

```text
Desired State
      vs
Current State
```

Example:

```text
Desired Pods = 3
Current Pods = 2
```

A controller takes action to bring the current state toward the desired state.

```text
Before:
Pod 1
Pod 2

After:
Pod 1
Pod 2
Pod 3
```

### Society analogy

If the society requires three security guards and one leaves, management arranges another guard.

This is the basic idea of **reconciliation**.

# 10. Worker Node

A worker node is a machine where application workloads run.

```text
Worker Node
 |
 +-- kubelet
 +-- container runtime
 +-- kube-proxy
 |
 +-- Pods
      |
      +-- Containers
```

A node can be:

- Physical server
- Virtual machine
- Cloud instance such as EC2

---

# 11. kubelet

The **kubelet** is the agent running on a worker node.

It:

- Registers the node with the cluster
- Receives Pod/workload instructions
- Works with the container runtime
- Monitors Pods and containers
- Reports status back to the control plane

### Society analogy

The kubelet is like a **building supervisor** who makes sure the expected residents/workloads are actually present and reports problems to management.

---

# 12. Container Runtime

Kubernetes requires a container runtime to run containers.

Modern Kubernetes uses runtimes compatible with the **Container Runtime Interface (CRI)**.

A common runtime is:

```text
containerd
```

Conceptually:

```text
Kubernetes
    |
  kubelet
    |
    | CRI
    v
containerd
    |
    v
Containers
```

### Kubernetes and Docker

Kubernetes does not require Docker Engine as its container runtime.

Docker-built images can still be used because standard OCI-compatible container images are supported.

---

# 13. kube-proxy

**kube-proxy** is a networking component that helps implement Kubernetes Service networking on nodes.

Simplified:

```text
Client
  |
  v
Service
  |
  +-- Pod 1
  +-- Pod 2
  +-- Pod 3
```

It helps direct network traffic toward the appropriate backend Pods according to the cluster networking implementation.

### Society analogy

Think of it as a **reception/routing system** that helps direct visitors toward the correct service.

---

# 14. Pod

A **Pod is the smallest deployable unit in Kubernetes.**

A Pod normally contains one container:

```text
Pod
 |
 +-- Container
```

A Pod can also contain multiple tightly coupled containers:

```text
Pod
 |
 +-- Application Container
 +-- Sidecar Container
```

Containers in the same Pod share the Pod's network namespace and can communicate through `localhost`. They can also share volumes when configured.

### Society analogy

A Pod is like a **flat**. Usually one main resident/service lives there, but multiple closely related services can share the same flat.

---

# 15. Container

The container contains the actual application process.

Example:

```text
Pod
 |
 +-- Nginx Container
```

or:

```text
Pod
 |
 +-- Java Application Container
```

Kubernetes manages Pods; the container runtime runs the containers inside them.

# 17. Desired State vs Current State

One of Kubernetes' most important concepts is **desired state**.

Suppose we declare:

```text
replicas: 3
```

Kubernetes attempts to maintain:

```text
Desired State = 3 Pods
```

If one Pod fails:

```text
Desired = 3
Current = 2
```

A controller works to restore:

```text
Desired = 3
Current = 3
```

This continuous reconciliation is a fundamental Kubernetes concept.

---

# 18. Declarative vs Imperative

### Imperative

You tell the system exactly what action to take:

```bash
docker run -d nginx
docker stop nginx
docker rm nginx
```

### Declarative

You describe the desired result:

```yaml
replicas: 3
image: nginx
```

Kubernetes continuously works toward that state.

Typical relationship:

```text
Deployment
    |
 ReplicaSet

 +-- Pod
```

# 20. ReplicaSet

A ReplicaSet ensures that the desired number of Pod replicas exist.

Example:

```text
replicas = 3

ReplicaSet
 |
 +-- Pod 1
 +-- Pod 2
 +-- Pod 3
```

If one Pod disappears:

```text
Desired = 3
Current = 2
```

The ReplicaSet/controller mechanism creates a replacement.

---

# 21. Service

Pods are temporary and their IP addresses can change.

A Kubernetes **Service** provides a stable network endpoint for accessing Pods.

```text
                 Service
                    |
          +---------+---------+
          |         |         |
        Pod 1     Pod 2     Pod 3
```

Common Service types:

- ClusterIP
- NodePort
- LoadBalancer
- ExternalName

---

# 22. Namespace

Namespaces logically separate resources within a cluster.

```text
Cluster
 |
 +-- dev
 |    +-- Pods
 |    +-- Services
 |
 +-- test
 |    +-- Pods
 |    +-- Services
 |
 +-- prod
      +-- Pods
      +-- Services
```

They are useful for environment, team, or application separation.

# 23. ConfigMap

A ConfigMap stores non-sensitive configuration.

Example:

```text
ConfigMap
 |
 +-- APP_MODE=production
 +-- LOG_LEVEL=INFO
```

Applications can consume ConfigMaps as environment variables or mounted files.

---

# 24. Secret

A Secret is intended for sensitive values such as:

- Passwords
- Tokens
- API keys
- Credentials

Example:

```text
Secret
 |
 +-- DB_PASSWORD
 +-- API_TOKEN
```

Secrets should be protected using appropriate RBAC, encryption-at-rest configuration, and access controls.

# 25. Kubernetes Networking – Basic Concept

Pods normally receive their own IP addresses.

Example:

```text
Pod 1 → 10.244.1.10
Pod 2 → 10.244.1.11
Pod 3 → 10.244.2.10
```

A Service provides a stable endpoint:

```text
Client
  |
  v
Service
  |
  +-- Pod 1
  +-- Pod 2
  +-- Pod 3
```

The exact Pod CIDR and networking behavior depend on the cluster's CNI/network implementation.

```text
replicas = 3
```

Scale to five:

```bash
kubectl scale deployment nginx --replicas=5
```

Kubernetes creates additional Pods.

```text
Before:
Pod 1
Pod 2
Pod 3

After:
Pod 1
Pod 2
Pod 3
Pod 4
Pod 5
```

The **Horizontal Pod Autoscaler (HPA)** can automate scaling based on configured metrics.

# 27. Self-Healing

If a workload managed by a controller fails, Kubernetes can recreate it.

```text
Pod 1
Pod 2
Pod 3
```

Pod 2 fails:

```text
Pod 1
Pod 3
```

Controller detects:

```text
Desired = 3
Current = 2
```

A replacement is created:

```text
Pod 1
Pod 3
Pod 4
```

---

# 28. Rolling Updates

Suppose the application currently uses:

```text
nginx:v1
```

We deploy:

```text
nginx:v2
```

A Deployment can gradually replace old Pods.

```text
v1  v1  v1
 |
v2  v1  v1
 |
v2  v2  v1
 |
v2  v2  v2
```

This helps achieve controlled deployments with reduced downtime.

---

# 29. Rollback

Useful commands:

```bash
kubectl rollout status deployment nginx
kubectl rollout history deployment nginx
kubectl rollout undo deployment nginx
```

Modern Kubernetes does not require Docker Engine as the container runtime.

```text
Kubernetes
    |
  kubelet
    |
    | CRI
    v
```

# 39. Scenario-Based Questions

### Scenario 1 – Pod crashes

You have 3 Pods and one fails.

**What happens?**

A controller managing the workload notices that the current state does not match the desired state and works to create/reconcile a replacement Pod.

### Scenario 2 – Need 10 copies

Use a Deployment with:

```yaml
replicas: 10
```

### Scenario 3 – Pod IP changes

Use a Kubernetes Service to provide a stable endpoint.

### Scenario 4 – Expose application outside cluster

Possible options include:

- NodePort
- LoadBalancer
- Ingress/Gateway-based architecture

The choice depends on requirements and environment.

### Scenario 5 – Different environments

Use namespaces and environment-specific configuration such as ConfigMaps and Secrets.
