# EKS + NGINX Troubleshooting Notes

## 1. Objective

The goal was to:

1. Provision an Amazon EKS cluster using Terraform.
2. Create and stabilize an EKS managed node group.
3. Enable the CoreDNS managed add-on.
4. Deploy an NGINX application using Terraform.
5. Expose NGINX publicly through an AWS Network Load Balancer.
6. Troubleshoot Terraform replacement failures, EC2 quota issues, Kubernetes scheduling issues, and AWS Load Balancer Controller configuration.

# 8. Root Cause: EC2 vCPU Quota

A later `describe-nodegroup` showed the real blocker:

```text
code: AsgInstanceLaunchFailures
message: Could not launch On-Demand Instances.
VcpuLimitExceeded - You have requested more vCPU capacity than your current vCPU limit of 8 allows...
```

The quota was verified with:

```bash
aws service-quotas get-service-quota \
  --service-code ec2 \
  --quota-code L-1216C47A \
  --region ap-south-1 \
  --query 'Quota.{Name:QuotaName,Limit:Value}' \
  --output table
```

Result:

```text
Running On-Demand Standard instances
Limit: 8.0
```

This was the main infrastructure root cause.

---

# 9. Why the Quota Problem Happened

The worker nodes were `t3.micro`.

Each `t3.micro` has 2 vCPUs.

Four running nodes consumed:

```text
4 nodes × 2 vCPU = 8 vCPU
```

The account quota was also:

```text
8 vCPU
```

So when Terraform tried to create a replacement node group, AWS could not launch any more instances.

This caused repeated:

```text
VcpuLimitExceeded
```

errors and multiple failed replacement node groups.

# 20. Installing AWS Load Balancer Controller with Terraform

The IAM module initially failed because the old module path was used:

```text
iam-role-for-service-accounts-eks
```

With IAM module v6.x, the correct path became:

```hcl
source = "terraform-aws-modules/iam/aws//modules/iam-role-for-service-accounts"
```

The v6 configuration used:

```hcl
name = "AmazonEKSLoadBalancerControllerRole"

policies = {
  load_balancer_controller = aws_iam_policy.aws_load_balancer_controller.arn
}
```

instead of older attributes such as:

```text
role_name
role_policy_arns
```

# 21. AWS Load Balancer Controller Terraform

Key resources included:

```hcl
resource "aws_iam_policy" "aws_load_balancer_controller" {
  name        = "AWSLoadBalancerControllerIAMPolicy"
  description = "IAM policy for AWS Load Balancer Controller"

  policy = file("${path.module}/iam_policy.json")
}
```

IRSA role:

```hcl
module "aws_load_balancer_controller_irsa_role" {
  source  = "terraform-aws-modules/iam/aws//modules/iam-role-for-service-accounts"
  version = "~> 6.8"

  name = "AmazonEKSLoadBalancerControllerRole"

  policies = {
    load_balancer_controller = aws_iam_policy.aws_load_balancer_controller.arn
  }

  oidc_providers = {
    main = {
      provider_arn = module.eks.oidc_provider_arn

      namespace_service_accounts = [
        "kube-system:aws-load-balancer-controller"
      ]
    }
  }
}
```

Service account:

```hcl
resource "kubernetes_service_account_v1" "aws_load_balancer_controller" {
  metadata {
    name      = "aws-load-balancer-controller"

      "eks.amazonaws.com/role-arn" = module.aws_load_balancer_controller_irsa_role.arn

```

# 34. Terraform State Lock Issue

At the end, running:

```bash
terraform plan
```

returned:

```text
Error acquiring the state lock
Operation: OperationTypeApply
```

This happened because `terraform apply` was still running in another terminal.

Important rule:

**Never use `terraform force-unlock` while a real Terraform process is still running.**

Check:

```bash
ps -ef | grep '[t]erraform'
```

If an apply is still active, wait for it to complete.

Only consider:

```bash
terraform force-unlock <LOCK_ID>
```

if:

1. No Terraform process is running.
2. The lock is confirmed stale.

Avoid:

```bash
terraform plan -lock=false
```

unless there is a very specific reason, because this bypasses Terraform's state protection.

# 35. Important Lessons Learned

## Terraform

- Always inspect `terraform plan` before applying.
- Deposed objects usually mean a previous replacement was only partially successful.
- `terraform state show` is essential to determine which actual AWS resource Terraform currently owns.
- Do not manually delete Terraform-managed resources without first understanding state.
- Avoid concurrent Terraform operations against the same state.

## EKS Managed Node Groups

- `CREATE_FAILED` does not always mean the EC2 nodes never joined Kubernetes.
- A node can eventually become `Ready` even after EKS has already declared node-group creation failed.
- Repeated retries can create multiple stale node groups and Auto Scaling Groups.

## AWS EC2 Quotas

- Always consider EC2 vCPU quota during node-group replacement.
- Create-before-destroy temporarily requires both old and new nodes to exist.
- With an 8-vCPU quota and 2-vCPU workers, four workers consume the entire quota.

Useful check:

```bash
aws service-quotas get-service-quota \
  --service-code ec2 \
  --quota-code L-1216C47A \
  --region ap-south-1
```

## Kubernetes Scheduling

`Pending` pods should always be investigated with:

```bash
kubectl describe pod <pod> -n <namespace>
```

or:

```bash
kubectl get events -n <namespace> --sort-by='.lastTimestamp'
```

Important scheduler messages include:

```text
Insufficient cpu
Insufficient memory
Too many pods
Untolerated taint
Node affinity conflict
```

In this case the exact cause was:

```text
Too many pods
```

## Pod Density

Checking `MAXPODS` is important:

```bash
kubectl get nodes \
  -o custom-columns=NAME:.metadata.name,MAXPODS:.status.capacity.pods
```

`t3.micro`:

```text
MAXPODS = 4
```

`t3.small` in this cluster:

```text
MAXPODS = 11
```

The system pods alone consumed all four pod slots on `t3.micro`.

## AWS Load Balancer Controller

A Service with:

```hcl
type = "LoadBalancer"
```

plus annotations such as:

```hcl
"service.beta.kubernetes.io/aws-load-balancer-type"            = "external"
"service.beta.kubernetes.io/aws-load-balancer-nlb-target-type" = "ip"
"service.beta.kubernetes.io/aws-load-balancer-scheme"          = "internet-facing"
```

requires a correctly installed AWS Load Balancer Controller.

Verify:

```bash
kubectl get deployment -n kube-system aws-load-balancer-controller
```

## NLB Troubleshooting Order

When an external NLB exists but the browser cannot reach the application:

1. Check the Service.
2. Check Service endpoints / EndpointSlices.
3. Check pods are Running.
4. Check scheduler events.
5. Check NLB scheme.
6. Check target group health.
7. Check subnet routing / security only after backend health is confirmed.

This order avoids debugging AWS networking when the real problem is simply a Pending Kubernetes pod.
