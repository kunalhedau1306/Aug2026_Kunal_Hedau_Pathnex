## 1. CI/CD concepts

### 1.1 What CI/CD means

**CI/CD** is a set of practices that automates the build, test, delivery, and deployment of software changes.

| Term | Meaning | Primary goal |
|---|---|---|
| **Continuous Integration (CI)** | Developers merge small changes frequently into a shared repository. Each change triggers automated build and test steps. | Detect integration problems early. |
| **Continuous Delivery** | Every successfully validated change is packaged and ready for release. Production deployment is normally approved manually. | Make releases low-risk and repeatable. |
| **Continuous Deployment** | Every validated change is automatically deployed to production without a manual release approval. | Deliver changes quickly and consistently. |

> Continuous delivery is not the same as continuous deployment. The former keeps a release *deployable*; the latter automatically deploys it.

### 1.2 Why CI/CD is useful

- Faster feedback when a build, test, security scan, or deployment fails.
- Fewer manual, error-prone release steps.
- Consistent build artifacts across ACC, PRE, and PRD.
- Traceability: commit, pipeline run, artifact version, approver, and deployment record can be linked to a Jira ticket.
- Safer releases through automated tests, quality gates, approvals, and rollback plans.

### 1.3 Typical CI/CD pipeline

```text
Developer commit / pull request
          ↓
Checkout source code
          ↓
Build and unit test (CI)
          ↓
Code quality + security scans
          ↓
Package/version artifact
          ↓
Publish artifact repository
          ↓
Deploy to non-production
          ↓
Integration / smoke tests
          ↓
Approval gate (continuous delivery)
          ↓
Deploy to production + validate
```

### 1.4 Essential pipeline stages

| Stage | Typical activities | Example tools |
|---|---|---|
| Source | Branching, pull requests, peer review | GitHub, Bitbucket |
| Build | Compile source, resolve dependencies | Maven, Gradle, npm |
| Test | Unit, integration, API, UI tests | JUnit, pytest, Postman/Newman |
| Quality | Static analysis, coverage, linting | SonarQube, Checkstyle |
| Security | Dependency, secret, container, IaC scans | OWASP Dependency-Check, Trivy, Gitleaks |
| Package | Produce an immutable versioned artifact | JAR/WAR, ZIP, container image |
| Publish | Store artifact for promotion | Nexus, Artifactory, GitHub Packages, ECR |
| Deploy | Apply a controlled deployment | Ansible, Helm, Terraform, WLST |
| Verify | Health checks, smoke tests, monitoring | curl, Checkmk, synthetic tests |

### 1.5 Core terms

- **Pipeline as code:** Pipeline definition stored with source code, such as `Jenkinsfile` or `.github/workflows/build.yml`.
- **Agent/runner:** Machine or container that executes pipeline jobs.
- **Artifact:** Immutable output of a build, e.g., `myapp-2.4.1.war`.
- **Environment:** Target stage such as DEV, ACC, PRE, or PRD.
- **Promotion:** Deploying the *same* tested artifact to the next environment; do not rebuild separately per environment.
- **Quality gate:** A rule that blocks a pipeline, e.g., test failure, critical vulnerability, or insufficient code coverage.
- **Idempotency:** Running the same deployment again produces the same intended state.
- **Rollback:** Returning to the previous known-good version after a failed release.
- **Secrets:** Passwords, tokens, private keys, or certificates. Store them in a credential vault, never in Git or pipeline logs.

### 1.6 Good CI/CD design principles

1. Keep commits small and build every pull request.
2. Treat configuration and pipelines as version-controlled code.
3. Build once; promote one immutable artifact.
4. Fail fast: run quick checks before slow deployment tests.
5. Separate application code from environment-specific configuration and secrets.
6. Require PR review and protected branches for production-bound code.
7. Use least-privilege credentials and short-lived tokens where possible.
8. Make production releases auditable: Jira/change ticket, approval, artifact checksum, deployment logs, and validation evidence.
9. Automate smoke checks and have a tested rollback procedure.
10. Avoid exposing secrets through `echo`, shell tracing (`set -x`), or verbose build output.

## 2. Jenkins overview

### 2.1 What Jenkins is

**Jenkins** is an open-source automation server commonly used for CI/CD. It coordinates jobs and pipelines, stores credentials, triggers builds from source-control events, and can execute commands on agents.

Jenkins supports:

- Freestyle jobs for simple or legacy automation.
- Declarative and scripted pipelines in a `Jenkinsfile`.
- Distributed execution through build agents.
- Webhooks from Git hosting platforms.
- Integrations with Ansible, Docker, Kubernetes, AWS, artifact repositories, scanners, and notification systems.

### 2.2 Jenkins controller and agents

| Component | Responsibility |
|---|---|
| **Controller** | Web UI, scheduling, configuration, credentials, plugin management, and job orchestration. |
| **Agent** | Executes builds, tests, scans, or deployments. It may be a VM, container, Kubernetes pod, or another EC2 instance. |
| **Executor** | A slot on controller/agent that runs one build at a time. |

For production use, avoid running heavy builds directly on the controller. Use dedicated, disposable agents where practical.

## 3. Jenkins installation on Amazon EC2

### 3.1 Reference architecture

For a small learning or internal setup:

```text
Administrator browser ─HTTPS─> Jenkins EC2 controller
                                  ├─ GitHub / Bitbucket
                                  ├─ Artifact repository
                                  ├─ Security scanners
                                  └─ SSH / Ansible / cloud agents
```

For enterprise use, place Jenkins behind an HTTPS reverse proxy or load balancer, use a managed database only where required by an integrated component, back up `JENKINS_HOME`, and run builds on separate agents.

### 3.2 EC2 prerequisites

- AWS account permissions to create an EC2 instance, security group, storage, and IAM role.
- A supported Linux AMI (for example, Amazon Linux 2023 or RHEL-compatible distribution).
- At least **t3.medium** for a small controller; increase CPU, memory, and EBS volume for concurrent jobs/plugins.
- An EBS volume sized for build history, artifacts, workspace cache, and logs. Avoid keeping long-term artifacts only on the controller.
- Java version supported by the chosen Jenkins LTS release (current Jenkins documentation specifies supported Java releases; verify before installation).
- Network access to Git server, package repositories, artifact repositories, deployment targets, and required scanners.

### 3.3 Security group guidance

| Traffic | Port | Source | Notes |
|---|---:|---|---|
| SSH administration | 22 | Bastion host or administrator VPN range only | Prefer AWS Systems Manager Session Manager where available. |
| Jenkins web UI | 8080 | Admin VPN range only | Use temporarily for initial setup only. |
| HTTPS via reverse proxy / ALB | 443 | Approved corporate ranges | Recommended normal user access path. |
| Jenkins agent inbound TCP | 50000 | Only Jenkins agents, if inbound agents are used | Do not expose to the internet. |

Do **not** expose TCP 8080, 50000, or SSH to `0.0.0.0/0`.

### 3.4 Create the EC2 instance

1. In AWS EC2, launch a supported Linux instance in the intended VPC and private subnet.
2. Attach an IAM role only with permissions Jenkins actually needs. For example, use narrowly scoped access to a specific S3 bucket or ECR repository rather than broad administrator access.
3. Attach an encrypted EBS volume; enable EBS snapshots or another approved backup process.
4. Attach the restrictive security group described above.
5. Configure DNS, NTP, OS patching, monitoring, vulnerability scanning, and central logging according to organisational standards.
6. Connect through a bastion host or AWS Systems Manager. Do not rely on a public IP for normal administration.

### 3.5 Install Jenkins on Amazon Linux 2023 (example)

The commands below are an example for Amazon Linux 2023. Check the current Jenkins LTS installation documentation and Java support matrix before executing in a production environment.

```bash
# Update OS packages
sudo dnf update -y

# Install a supported Java runtime (commonly Java 21 for current Jenkins LTS)
sudo dnf install -y java-21-amazon-corretto-headless fontconfig

# Add the Jenkins stable RPM repository and signing key
sudo curl -fsSL -o /etc/yum.repos.d/jenkins.repo \
  https://pkg.jenkins.io/redhat-stable/jenkins.repo
sudo rpm --import https://pkg.jenkins.io/redhat-stable/jenkins.io-2023.key

# Install Jenkins
sudo dnf install -y jenkins

# Start at boot and start immediately
sudo systemctl enable --now jenkins

# Verify service status and listening port
sudo systemctl status jenkins --no-pager
sudo ss -lntp | grep 8080
```

Initial administrator password:

```bash
sudo cat /var/lib/jenkins/secrets/initialAdminPassword
```

Open `http://<jenkins-host>:8080` only from the approved administration network, paste the initial password, install the suggested plugins as a starting point, and create the first administrator account.

### 3.6 Post-installation hardening checklist

- Put Jenkins behind HTTPS (ALB, Nginx, Apache httpd, or another approved reverse proxy).
- Set the correct public **Jenkins URL** under *Manage Jenkins → System*.
- Enable SSO/LDAP/OIDC integration where available; avoid shared local administrator accounts.
- Configure role-based access control and use least privilege.
- Store tokens, passwords, SSH keys, and cloud credentials in Jenkins Credentials or an approved external secret manager.
- Disable anonymous read access unless a documented use case requires it.
- Keep Jenkins LTS, plugins, Java, and the operating system patched.
- Back up `JENKINS_HOME` (typically `/var/lib/jenkins`) consistently, including job configuration, credentials key material, and controller configuration. Test restoration.
- Configure log rotation, monitoring, alerting, disk-space thresholds, and an audit trail.
- Configure agent labels and prevent untrusted code from running on privileged deployment agents.
- Use multibranch pipelines and protected source-control branches.

### 3.7 Reverse proxy notes

When Jenkins is published through HTTPS, ensure the proxy forwards the original protocol and host headers. Jenkins must be configured with its external HTTPS URL; otherwise webhook URLs, redirects, and agent connections can fail.

### 3.8 Basic Jenkins operational commands

```bash
# Service state
sudo systemctl status jenkins
sudo systemctl restart jenkins

# Service logs
sudo journalctl -u jenkins -f

# Disk usage of Jenkins home
sudo du -sh /var/lib/jenkins
```

## 4. Jenkins pipelines

### 4.1 Declarative pipeline example

Save the following file as `Jenkinsfile` in the repository root:

```groovy
pipeline {
    agent any

    options {
        timestamps()
        disableConcurrentBuilds()
    }

    environment {
        APP_NAME = 'example-service'
        VERSION  = "${BUILD_NUMBER}"
    }

    stages {
        stage('Checkout') {
            steps {
                checkout scm
            }
        }

        stage('Build') {
            steps {
                sh 'mvn -B clean package -DskipTests'
            }
        }

        stage('Unit tests') {
            steps {
                sh 'mvn -B test'
            }
            post {
                always {
                    junit 'target/surefire-reports/*.xml'
                }
            }
        }

        stage('Publish artifact') {
            when {
                branch 'main'
            }
            steps {
                archiveArtifacts artifacts: 'target/*.jar', fingerprint: true
            }
        }

        stage('Deploy ACC') {
            when {
                branch 'main'
            }
            steps {
                sh 'ansible-playbook -i inventories/acc deploy.yml --extra-vars version=$VERSION'
            }
        }
    }

    post {
        success {
            echo "Pipeline succeeded for ${APP_NAME} ${VERSION}"
        }
        failure {
            echo 'Pipeline failed. Review the stage logs before retrying.'
        }
        always {
            cleanWs()
        }
    }
}
```

Key points:

- `agent any` selects any eligible Jenkins executor; production pipelines should often use a specific labelled agent.
- `when { branch 'main' }` prevents publishing/deployment from feature branches.
- `junit` publishes test results even if a test fails.
- `archiveArtifacts` is convenient for simple use, but an artifact repository is preferred for release artifacts.
- Do not pass secrets through `--extra-vars`, command lines, or logs. Use credential bindings and secret stores.

## 5. Useful Jenkins plugins

Install only plugins with a clear need, review their maintenance/security status, and patch them regularly. Every plugin expands the Jenkins attack surface.

| Plugin | Why it is useful | Typical use |
|---|---|---|
| **Pipeline** | Provides Pipeline-as-Code capabilities. | Declarative or scripted `Jenkinsfile` pipelines. |
| **Git** | Enables Git checkout and polling. | Clone GitHub/Bitbucket repositories. |
| **GitHub** | GitHub integration and webhook support. | Trigger builds from push/PR events. |
| **GitHub Branch Source** | Discovers branches and pull requests. | Multibranch pipelines and GitHub organisations. |
| **Credentials Binding** | Injects credentials into a build securely. | Use SSH key, username/password, token, or secret text variables. |
| **SSH Agent** | Makes SSH credentials available to shell commands. | Controlled SSH deployment to Linux servers. |
| **Pipeline Utility Steps** | Extra pipeline steps for files, JSON, YAML, ZIP, etc. | Read/write metadata and package files. |
| **Workspace Cleanup** | Cleans workspaces reliably. | Remove old source and sensitive temporary content. |
| **JUnit** | Publishes JUnit-compatible test reports. | Display Maven, Gradle, pytest test results. |
| **HTML Publisher** | Publishes generated HTML reports. | Test, coverage, or lint reports. |
| **SonarQube Scanner** | Integrates code analysis and quality gates. | Static analysis and coverage gate. |
| **OWASP Dependency-Check** | Finds known vulnerable dependencies. | Dependency vulnerability scan. |
| **Warnings Next Generation** | Aggregates static-analysis warnings. | Linting and code-quality reporting. |
| **Docker Pipeline** | Builds/runs images in pipelines. | Containerised builds or deployments. |
| **Kubernetes** | Dynamically creates Kubernetes-based agents. | Ephemeral build agents. |
| **Ansible** | Runs Ansible playbooks from Jenkins. | Infrastructure/application deployment automation. |
| **Configuration as Code (JCasC)** | Stores Jenkins configuration as YAML. | Reproducible controller setup. |
| **Job DSL** | Creates jobs from versioned DSL definitions. | Standardise large Jenkins estates. |
| **Build Timeout** | Stops hung jobs. | Protect agents and executors. |
| **Timestamper** | Adds timestamps to build logs. | Troubleshooting and audit evidence. |
| **Email Extension** | Flexible email notifications. | Alert owners for failed deployments. |
| **Slack Notification** | Sends pipeline notifications to Slack. | Team notifications where approved. |

### Plugin selection rules

- Prefer built-in features where sufficient.
- Use the Jenkins LTS release line and compatible plugin versions.
- Remove unused plugins, not merely disable them.
- Test Jenkins/plugin updates in a non-production controller first.
- Subscribe to Jenkins security advisories and remediate vulnerable plugins promptly.
- For high-value environments, restrict who can install plugins and who can run arbitrary pipeline code.

## 6. GitHub Actions

### 6.1 What GitHub Actions is

**GitHub Actions** is GitHub's integrated automation platform. A workflow is defined as YAML in the repository under:

```text
.github/workflows/<workflow-name>.yml
```

It can build, test, scan, package, publish, and deploy code based on repository events or manual triggers.

### 6.2 Main components

| Component | Description |
|---|---|
| **Workflow** | YAML automation definition in `.github/workflows/`. |
| **Event** | Trigger, e.g., `push`, `pull_request`, `workflow_dispatch`, or a schedule. |
| **Job** | Group of steps executed on one runner. Jobs can run in parallel or depend on other jobs. |
| **Step** | Individual command or reusable action in a job. |
| **Action** | Reusable unit of automation, such as `actions/checkout`. |
| **Runner** | Host that runs the job: GitHub-hosted or self-hosted. |
| **Secret** | Encrypted value supplied at runtime; available as `secrets.NAME`. |
| **Environment** | Deployment boundary with protection rules, reviewers, and scoped secrets. |

### 6.3 Jenkins vs GitHub Actions

| Area | Jenkins | GitHub Actions |
|---|---|---|
| Hosting | Self-managed controller and agents. | GitHub-hosted service or self-hosted runners. |
| Configuration | `Jenkinsfile` (Groovy) plus controller configuration. | YAML inside the GitHub repository. |
| Flexibility | Extremely broad plugin ecosystem and customisation. | Deep native GitHub integration; marketplace actions. |
| Operations | You patch, back up, secure, and monitor Jenkins. | GitHub operates hosted runners/control plane; self-hosted runners remain your responsibility. |
| Best fit | Complex legacy integrations, multi-SCM, central shared automation. | GitHub-centric repositories and straightforward cloud-native workflows. |

Both can coexist. Avoid making both systems deploy the same application independently without a clearly defined ownership model.

### 6.4 Basic GitHub Actions workflow

Create `.github/workflows/ci.yml`:

```yaml
name: Java CI

on:
  pull_request:
    branches: [main]
  push:
    branches: [main]
  workflow_dispatch:

permissions:
  contents: read

jobs:
  build-and-test:
    runs-on: ubuntu-latest

    steps:
      - name: Check out source
        uses: actions/checkout@v4

      - name: Set up Java
        uses: actions/setup-java@v4
        with:
          distribution: temurin
          java-version: '21'
          cache: maven

      - name: Build and test
        run: mvn -B verify

      - name: Upload test reports
        if: always()
        uses: actions/upload-artifact@v4
        with:
          name: test-reports
          path: target/surefire-reports/
          if-no-files-found: warn
```

### 6.5 Deployment workflow with protection

```yaml
name: Deploy ACC

on:
  workflow_dispatch:
    inputs:
      version:
        description: Artifact version to deploy
        required: true
        type: string

permissions:
  contents: read

jobs:
  deploy-acc:
    runs-on: [self-hosted, linux, deployment]
    environment: acc

    steps:
      - uses: actions/checkout@v4

      - name: Deploy selected version
        env:
          DEPLOY_TOKEN: ${{ secrets.DEPLOY_TOKEN }}
          VERSION: ${{ inputs.version }}
        run: |
          ./scripts/deploy-acc.sh "$VERSION"
```

Configure the GitHub `acc` environment with required reviewers and scoped secrets. This gives an approval gate before the job receives its environment secrets.

### 6.6 GitHub Actions security practices

1. Set explicit minimal `permissions:` for each workflow; do not default to write access.
2. Pin third-party actions to a full commit SHA for stronger supply-chain control; review and update the pin through a managed process.
3. Use GitHub Environments for ACC/PRE/PRD approvals and environment-specific secrets.
4. Use OpenID Connect (OIDC) for AWS/cloud authentication where possible, instead of long-lived cloud keys.
5. Never print secrets. Masking reduces accidental exposure but is not a substitute for safe handling.
6. Treat pull-request code as untrusted, especially from forks. Do not expose deployment credentials to it.
7. Protect `main` and release branches with PR reviews, required status checks, and signed commits where required.
8. Keep self-hosted runners isolated, patched, ephemeral where possible, and dedicated by trust level. Do not run untrusted pull-request workflows on production deployment runners.
9. Use dependency and secret scanning, plus code-review policies, before deployment.

## 7. Suggested practical implementation

For an enterprise Java/WebLogic application, a practical release pattern is:

1. Developer creates a feature branch and pull request.
2. CI validates formatting, unit tests, dependency vulnerabilities, secret scan, and code quality.
3. Merge to `main` creates one versioned WAR/EAR artifact and publishes it to the approved artifact repository.
4. A controlled deployment workflow deploys that exact version to ACC using Ansible/WLST.
5. Automated health checks, log checks, and smoke tests provide evidence.
6. The tested artifact is promoted to PRE, then PRD, with change/Jira references and required approvals.
7. Post-deployment checks validate service endpoints, WebLogic deployment state, database connectivity, and monitoring status.
8. If validation fails, the pipeline halts and executes/assists a documented rollback to the prior artifact version.

### Example repository layout

```text
application-repository/
├── src/
├── pom.xml
├── Jenkinsfile
├── .github/
│   └── workflows/
│       ├── ci.yml
│       └── deploy-acc.yml
├── ansible/
│   ├── inventories/
│   │   ├── acc/
│   │   ├── pre/
│   │   └── prd/
│   └── deploy.yml
├── scripts/
│   ├── smoke-test.sh
│   └── rollback.sh
└── docs/
    └── release-runbook.md
```
