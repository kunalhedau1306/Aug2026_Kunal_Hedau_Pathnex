## 1. Amazon Redshift

Amazon Redshift is a fully managed cloud data warehouse designed for large-scale analytics and SQL-based reporting. It is primarily optimized for **OLAP (Online Analytical Processing)** workloads.

```text
Operational Databases
       |
       v
   ETL / DMS
       |
       v
  Amazon Redshift
       |
       v
 BI / Analytics / Reports
```

### OLTP vs OLAP

| OLTP | OLAP |
|---|---|
| Online Transaction Processing | Online Analytical Processing |
| Application transactions | Analytics/reporting |
| Many small reads/writes | Large analytical queries |
| Current operational data | Historical/aggregated data |
| Example: order processing | Example: sales analysis |

### Redshift Serverless

Redshift Serverless provides analytics without requiring you to provision and manage a traditional provisioned cluster.

**Provisioned vs Serverless**

| Provisioned | Serverless |
|---|---|
| Manage provisioned compute | AWS manages capacity |
| Good for predictable workloads | Good for variable/intermittent workloads |
| Cluster-oriented | Workgroup-oriented |
| More configuration | Less infrastructure management |

### Common use cases

- Business intelligence
- Sales analytics
- Customer analytics
- Financial reporting
- Historical reporting
- Data warehouse workloads

## 2. AWS Database Migration Service (AWS DMS)

AWS DMS helps migrate databases and data stores to AWS or between supported database environments.

It supports:
- Homogeneous migrations
- Heterogeneous migrations
- Ongoing replication
- Change Data Capture (CDC)

### Basic architecture

```text
Source Database
      |
      v
Source Endpoint
      |
      v
Replication Instance
      |
      v
Target Endpoint
      |
      v
Target Database
```

### DMS components

**Source Endpoint:** Connection information for the source.

**Target Endpoint:** Connection information for the target.

**Replication Instance:** AWS-managed compute resource used by DMS.

**Replication Task:** Defines what should be migrated and how replication operates.

### Homogeneous migration

Same database engine:

```text
Oracle
  |
 DMS
  v
Oracle
```

### Heterogeneous migration

Different database engines:

```text
Oracle
  |
 DMS + schema conversion/assessment as needed
  v
PostgreSQL
```

DMS moves/replicates data, while schema objects and application-specific database code may require additional assessment or conversion.

### Migration types

**Full Load**

Copies existing data.

```text
Source ---- Full Load ----> Target
```

**Full Load + CDC**

Copies existing data and then continuously captures changes.

```text
Existing Data
     |
     v
Full Load
     |
     v
Target
     ^
     |
    CDC
     |
Source Changes
```

**CDC Only**

Replicates changes when the target has already been prepared appropriately.

### CDC

Change Data Capture can replicate supported changes such as:

- INSERT
- UPDATE
- DELETE

CDC is useful when minimizing application downtime during migration.

### Typical migration strategy

```text
Assess source
     |
     v
Prepare target
     |
     v
Configure DMS
     |
     v
Full load
     |
     v
Monitor CDC
     |
     v
Validate target
     |
     v
Application cutover
```

## 3. Amazon EBS

Amazon Elastic Block Store provides persistent **block storage** for EC2.

Think of EBS as a virtual hard disk.

```text
EC2 Instance
     |
    EBS
   Volume
```

Common uses:
- Operating system disks
- Application data
- Database storage
- File systems created on block devices

EBS volumes are associated with an Availability Zone and support snapshots.

Common volume families include:
- General Purpose SSD
- Provisioned IOPS SSD
- Throughput Optimized HDD
- Cold HDD

## 4. Amazon EFS

Amazon Elastic File System is a managed elastic file system for Linux workloads.

Multiple compute resources can access the same file system concurrently.

```text
        EFS
       / | \
      /  |  \
     v   v   v
   EC2  EC2  EC2
```

Common uses:
- Shared application files
- User uploads
- Shared configuration
- Web content
- Common application data

## 5. NFS

NFS stands for **Network File System**.

NFS is a **file-sharing protocol**, not an AWS storage service.

Amazon EFS supports NFS-based client access.

```text
EC2
 |
 | NFS
 v
EFS
```

### EBS vs EFS vs NFS

| EBS | EFS | NFS |
|---|---|---|
| Block storage | Managed file storage | File-sharing protocol |
| Virtual disk | Shared file system | Defines network file access |
| Commonly used with EC2 | Multiple clients | Used by file systems such as EFS |
| Good for OS/database disks | Good for shared files | Network protocol |

**Memory:**

```text
EBS = Disk
EFS = Shared File System
NFS = Protocol
```

### Example

Three EC2 servers need to access the same uploaded files:

```text
              Load Balancer
                    |
          +---------+---------+
          |         |         |
         EC2       EC2       EC2
          |         |         |
          +---------+---------+
                    |
                   EFS
                    |
              Shared Files
```

## 6. AWS Elastic Beanstalk

AWS Elastic Beanstalk is a managed application deployment service that simplifies deploying and operating web applications.

You provide application code and Elastic Beanstalk can provision/manage supporting AWS resources for the environment.

Depending on the platform/configuration, these can include:
- EC2
- Elastic Load Balancing
- Auto Scaling
- CloudWatch integration
- Security groups

```text
Developer
    |
    v
Application Code
    |
    v
Elastic Beanstalk
    |
    +---- EC2
    +---- Load Balancer
    +---- Auto Scaling
    +---- CloudWatch
```

Elastic Beanstalk is often described as **PaaS-like** because it abstracts much infrastructure management while still using underlying AWS resources.

### Important concepts

- Application
- Application version
- Environment
- Environment configuration
- Platform

```text
MyApplication
     |
     +---- Version 1
     +---- Version 2
     |
     +---- Test Environment
     +---- Production Environment
```

### Deployment policies

#### All at once

Updates all instances together.

- Fast
- Can cause downtime

#### Rolling

Updates instances in batches.

```text
Old Old Old Old
 |
 v
New Old Old Old
New New Old Old
New New New Old
New New New New
```

#### Rolling with additional batch

Uses additional capacity during deployment to help maintain availability.

#### Immutable

Creates a new set of instances for the new version and shifts traffic after the new environment is ready.

#### Blue/Green

Uses separate environments and switches traffic.

```text
Blue Environment
   Current
      |
   Traffic

Green Environment
   New Version

Switch traffic
      |
      v
Green = Production
```

### Elastic Beanstalk vs EC2

| Elastic Beanstalk | EC2 |
|---|---|
| Application deployment platform | Virtual server |
| Higher-level abstraction | Lower-level control |
| Manages/provisions environment resources | More infrastructure management |
| Easier application deployment | Greater infrastructure control |

## 7. Amazon CloudFront

Amazon CloudFront is AWS's **Content Delivery Network (CDN)**.

It distributes content through a global network of edge locations so users can retrieve content from locations closer to them.

```text
              Users
          /     |     \
         v      v      v
      Edge    Edge    Edge
      Location Locations
          \     |     /
           \    |    /
             Origin
        S3 / ALB / EC2
```

### Benefits

- Lower latency
- Faster content delivery
- Caching
- Reduced origin load
- Global distribution
- HTTPS/TLS
- Integration with AWS WAF

### CloudFront origin

An origin is the source from which CloudFront retrieves content.

Examples:
- Amazon S3
- Application Load Balancer
- EC2/application server
- Other supported HTTP origins

### Cache hit

Object is already cached at the edge.

```text
User
 |
 v
Edge
 |
 | Cache Hit
 v
Response
```

### Cache miss

Object is not cached, so CloudFront retrieves it from the origin.

```text
User
 |
 v
Edge
 |
 | Cache Miss
 v
Origin
 |
 v
Edge Cache
 |
 v
User
```

## 8. AWS Snowball

AWS Snowball is part of AWS's physical data transfer solutions. It uses physical devices to move large amounts of data into or out of AWS.

It is useful when transferring data over the network would take too long or be impractical.

Example:

```text
On-Premises
    |
    v
Snowball Device
    |
    v
Ship to AWS
    |
    v
AWS Data Center
    |
    v
Data Imported
```

### Example

Suppose an organization has 500 TB of data and limited internet bandwidth.

Instead of transferring all data online:

```text
500 TB
  |
  v
Snowball
  |
  v
Physical shipment
  |
  v
AWS
```

### Snowball vs online transfer

| Snowball | Online Transfer |
|---|---|
| Physical data transfer | Network transfer |
| Useful for very large datasets | Good for normal/continuous transfers |
| Depends on device logistics | Depends on network bandwidth |
| Can reduce long transfer times | No physical shipping |

### Important

AWS Snow Family offerings and device capabilities can change. For production planning, verify the current AWS offering and regional availability.

**Memory:** Snowball = physically move large datasets when network transfer is impractical.

## 9. AWS CodePipeline

AWS CodePipeline is a continuous delivery service used to automate application release workflows.

Typical pipeline:

```text
Source
  |
  v
Build
  |
  v
Test
  |
  v
Deploy
```

### Common stages

#### Source

Retrieves application source code.

Possible sources include:
- GitHub
- Bitbucket through supported integrations/connections
- Amazon S3
- Other supported source providers

#### Build

Builds/packages the application.

A common service is AWS CodeBuild.

#### Test

Runs automated tests.

#### Approval

A manual approval action can be added where required.

#### Deploy

Deploys the application.

Possible deployment targets include:
- Elastic Beanstalk
- EC2
- ECS
- Lambda
- CloudFormation

### Example

```text
Developer
    |
    v
Git Repository
    |
    v
CodePipeline
    |
    v
Source
    |
    v
CodeBuild
    |
    v
Automated Tests
    |
    v
Manual Approval
    |
    v
Elastic Beanstalk
```

### CodePipeline vs CodeBuild

| CodePipeline | CodeBuild |
|---|---|
| Orchestrates release workflow | Builds/tests code |
| Pipeline stages/actions | Build environment |
| Connects services together | Executes build commands |

**Memory:**

```text
CodePipeline = Pipeline manager
CodeBuild    = Build engine
```

### CodePipeline vs Jenkins

| CodePipeline | Jenkins |
|---|---|
| AWS managed service | Usually self-managed |
| AWS-native integrations | Large plugin ecosystem |
| Less infrastructure management | More administration |
| IAM integration | Jenkins security/configuration |

## 12. Storage Architecture Example

For an application with three EC2 servers that need both private disks and shared files:

```text
                Load Balancer
                      |
            +---------+---------+
            |         |         |
           EC2       EC2       EC2
            |         |         |
          EBS       EBS       EBS
            \         |         /
             \        |        /
                    EFS
                     |
               Shared Files
```

Use:
- **EBS** for instance-specific block storage.
- **EFS** for shared file storage.
- **NFS** as the network file protocol used by supported clients to access EFS.

## 17. Scenario-Based Questions

### Scenario 1 – Large Data Warehouse

A company collects billions of sales records and wants dashboards.

**Answer:** Amazon Redshift.

```text
Large historical data
        +
Analytics
        +
BI
        =
Redshift
```

### Scenario 2 – Database Migration

A company wants to migrate an on-premises database to AWS with minimal downtime.

Possible approach:

```text
Source DB
   |
   v
AWS DMS
   |
   +---- Full Load
   |
   +---- CDC
   |
   v
Target DB
```

### Scenario 3 – Shared Files

Three EC2 instances need access to the same uploaded files.

**Answer:** Amazon EFS.

### Scenario 4 – EC2 Database Disk

An EC2-hosted database needs persistent block storage.

**Answer:** EBS with the appropriate volume type/configuration.

### Scenario 5 – Global Website

Users are distributed across India, Europe and the US and static content should load quickly.

**Answer:** CloudFront.

### Scenario 6 – 100 TB Migration

An organization has a huge dataset and insufficient network bandwidth.

**Answer:** Evaluate Snowball/Snow Family physical transfer options.

### Scenario 7 – Application Deployment

Developers want to deploy a standard web application without manually building all the supporting infrastructure.

**Answer:** Elastic Beanstalk can simplify this.

### Scenario 8 – Automated Release

A developer pushes code and the organization wants:

```text
Source
  |
Build
  |
Test
  |
Deploy
```

**Answer:** CodePipeline, typically integrated with CodeBuild and a deployment target.

## 23. Key Takeaways

1. **Redshift is primarily an analytical data warehouse, not a normal OLTP database.**
2. **DMS migrates and can continuously replicate supported database workloads.**
3. **CDC is useful for keeping a target synchronized while a source remains active.**
4. **EBS is block storage; EFS is a managed shared file system; NFS is a protocol.**
5. **Elastic Beanstalk simplifies application deployment and environment management.**
6. **CloudFront is a CDN that caches and delivers content closer to users.**
7. **Snowball is useful for physically transferring very large datasets when network transfer is impractical.**
8. **CodePipeline orchestrates CI/CD stages such as source, build, test, approval and deployment.**
9. **CodePipeline and CodeBuild are complementary: Pipeline orchestrates; Build executes builds/tests.**
10. **DMS and Snowball solve different migration problems: DMS is database-aware migration/replication, while Snowball focuses on physical bulk data transfer.**
