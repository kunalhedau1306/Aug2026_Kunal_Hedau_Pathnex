# Day 15 – Kubernetes Workloads, Affinity, Taints & EKS Terraform Troubleshooting
## Date: 15-Aug-2026

## 1. Workload Controllers

### Deployment
Used mainly for stateless applications such as web servers, APIs and frontends.

```text
Deployment → ReplicaSet → Pods → Containers
```

Useful commands:

```bash
kubectl create deployment nginx --image=nginx --replicas=3
kubectl get deployment
kubectl get rs
kubectl get pods -o wide
kubectl scale deployment nginx --replicas=5
kubectl set image deployment/nginx nginx=nginx:1.27
kubectl rollout status deployment/nginx
kubectl rollout history deployment/nginx
kubectl rollout undo deployment/nginx
```

A Deployment provides declarative management, scaling, rolling updates and rollback.

### ReplicaSet
Maintains a desired number of matching Pods.

```text
ReplicaSet
  ├── Pod 1
  ├── Pod 2
  └── Pod 3
```

If one Pod disappears, the ReplicaSet creates a replacement. Normally, ReplicaSets are managed by Deployments rather than created directly.

### StatefulSet
Used for stateful workloads requiring stable identity and/or persistent storage characteristics.

Example Pod names:

```text
mysql-0
mysql-1
mysql-2
```

If `mysql-1` is recreated, its identity remains `mysql-1`.

Typical use cases:

- Databases
- Kafka
- Distributed stateful applications

StatefulSets are commonly combined with PersistentVolumeClaims:

```text
StatefulSet
 ├── Pod 0 → PVC 0 → PV
 ├── Pod 1 → PVC 1 → PV
 └── Pod 2 → PVC 2 → PV
```

### DaemonSet
Ensures a Pod runs on every eligible node.

Typical use cases:

- Logging agents
- Monitoring agents
- Security agents
- Node networking/storage agents

```text
Node 1 → agent Pod
Node 2 → agent Pod
Node 3 → agent Pod
```

Useful commands:

```bash
kubectl get daemonset
kubectl get pods -o wide
kubectl describe daemonset <name>
```

## 2. Controller Comparison

| Controller | Main purpose | Identity | Typical use |
|---|---|---|---|
| Deployment | Stateless applications | Not stable | Web/API |
| ReplicaSet | Maintain Pod count | Not stable | Usually managed by Deployment |
| StatefulSet | Stateful workloads | Stable | Database/distributed systems |
| DaemonSet | Node-level workload | Not the focus | Monitoring/logging agents |

Memory trick:

```text
Deployment → application replicas
ReplicaSet  → Pod count
StatefulSet → stable identity/state
DaemonSet   → one Pod per eligible node
```

# 3. Node Affinity

Node Affinity controls which nodes a Pod can or should run on based on node labels.

Label a node:

```bash
kubectl label node <node-name> workload=database
kubectl get nodes --show-labels
```

Example:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: affinity-pod
spec:
  affinity:
    nodeAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
        nodeSelectorTerms:
          - matchExpressions:
              - key: workload
                operator: In
                values:
                  - database
  containers:
    - name: nginx
      image: nginx
```

Two important forms:

```text
requiredDuringSchedulingIgnoredDuringExecution
→ hard requirement

preferredDuringSchedulingIgnoredDuringExecution
→ soft preference
```

If a required rule cannot be satisfied, the Pod remains Pending.

`IgnoredDuringExecution` means that a later change to node labels does not by itself cause an already-running Pod to be evicted.

# 4. Pod Affinity

Pod Affinity allows a Pod to be scheduled near other matching Pods.

Example:

```text
Backend Pod
     ↑
     | Pod Affinity
     |
Frontend Pod
```

Example:

```yaml
affinity:
  podAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
      - labelSelector:
          matchLabels:
            app: backend
        topologyKey: kubernetes.io/hostname
```

With `kubernetes.io/hostname`, the topology domain is the node.

Other topology choices can be used depending on the cluster labels and desired placement, such as availability-zone topology.

# 5. Pod Anti-Affinity

Pod Anti-Affinity helps keep matching Pods apart.

Example:

```text
web-1 → Node 1
web-2 → Node 2
web-3 → Node 3
```

This improves availability because a single node failure is less likely to affect all replicas.

Example:

```yaml
affinity:
  podAntiAffinity:
    preferredDuringSchedulingIgnoredDuringExecution:
      - weight: 100
        podAffinityTerm:
          labelSelector:
            matchLabels:
              app: web
          topologyKey: kubernetes.io/hostname
```

# 6. Affinity Summary

```text
Node Affinity
  → Pod wants/needs a particular type of node

Pod Affinity
  → Pod wants/needs to be near matching Pods

Pod Anti-Affinity
  → Pod wants to avoid matching Pods
```

# 7. Taints

A taint is placed on a node to repel Pods that do not tolerate it.

Example:

```bash
kubectl taint nodes worker1 dedicated=database:NoSchedule
```

Concept:

```text
Node
 |
 +-- Taint
      |
      X
  Non-tolerating Pod
```

# 8. Tolerations

A toleration is configured on a Pod and allows it to be scheduled on a matching tainted node.

```yaml
tolerations:
  - key: dedicated
    operator: Equal
    value: database
    effect: NoSchedule
```

Important:

> A toleration allows a Pod onto a tainted node; it does not force the Pod onto that node.

To target a dedicated node pool, combine a toleration with node affinity or nodeSelector.

# 9. Taint Effects

### NoSchedule

New non-tolerating Pods are not scheduled.

```text
Existing Pod → stays
New non-tolerating Pod → blocked
```

### PreferNoSchedule

Kubernetes tries to avoid the node for non-tolerating Pods, but it is a preference.

### NoExecute

Affects both new and existing Pods.

```text
New non-tolerating Pod → blocked
Existing non-tolerating Pod → may be evicted
```

Remove a taint:

```bash
kubectl taint nodes worker1 dedicated=database:NoSchedule-
```

# 10. Taint vs Toleration vs Affinity

```text
Taint
  → Node says: keep non-tolerating Pods away

Toleration
  → Pod says: I can tolerate this taint

Node Affinity
  → Pod says: I want/need this type of node

Pod Affinity
  → Pod says: place me near matching Pods

Pod Anti-Affinity
  → Pod says: keep me away from matching Pods
```

A common dedicated-node design:

```text
Database Node
 ├── Label: workload=database
 └── Taint: dedicated=database:NoSchedule

Database Pod
 ├── Toleration for dedicated=database
 └── Node Affinity for workload=database
```

This both permits and targets the correct node pool.

# 13. First EKS Troubleshooting Checks

```bash

```

fails, first identify the exact resource and AWS error.

Verify identity:

```bash

```

```bash
aws configure get region
```

```bash
aws eks list-clusters --region ap-south-2
```

Describe cluster:

```bash
aws eks describe-cluster   --name demo-eks   --region ap-south-2
```

Check status:

```bash
aws eks describe-cluster   --name demo-eks   --region ap-south-2   --query 'cluster.status'
```

Expected healthy status:

```text
ACTIVE
```

# 14. IAM Troubleshooting

Common error:

```text
AccessDeniedException
```

Check:

```bash
aws sts get-caller-identity
```

Then determine:

- Which IAM principal Terraform is using
- Which API call was denied
- Whether required permissions exist
- Whether an AWS Organizations SCP blocks the operation
- Whether a permissions boundary is restricting access
- Whether the wrong AWS profile/role is active


# 16. Security Group Troubleshooting

# 34. Key Takeaways

1. Deployment is primarily used for stateless applications.
2. ReplicaSet maintains the desired number of Pods.
3. Deployment normally manages ReplicaSets.
4. StatefulSet provides stable Pod identity and is suited to stateful workloads.
5. DaemonSet runs a Pod on each eligible node.
6. Node Affinity selects nodes using node labels.
7. Pod Affinity places Pods near matching Pods.
8. Pod Anti-Affinity helps distribute replicas.
9. Taints repel Pods from nodes.
10. Tolerations allow Pods to tolerate matching taints.
11. A toleration alone does not force a Pod onto a node.
12. Taint + Toleration + Node Affinity is a common dedicated-node pattern.
13. For Terraform EKS failures, identify the exact failing resource before changing configuration.
14. For node-group failures, `aws eks describe-nodegroup` and `health.issues` are especially useful.
15. If nodes are `NotReady`, inspect the node, kube-system Pods, CNI, kubelet and network path.
