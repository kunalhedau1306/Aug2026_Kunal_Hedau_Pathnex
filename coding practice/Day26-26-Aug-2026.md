# ELK Stack — Detailed Notes, Examples, and Workflow

**Date:** 26 August 2026  
**Audience:** Technical Application Management / DevOps learners

---

## 1. What is the ELK Stack?

**ELK** stands for:

- **E**lasticsearch — stores, indexes, searches, and analyses data.
- **L**ogstash — collects, parses, transforms, and forwards data.
- **K**ibana — searches, visualises, and manages data in Elasticsearch.

In practical deployments, ELK is commonly extended with **Beats** or **Elastic Agent**, which collect logs and metrics from servers. The broader product family is called the **Elastic Stack**.

The Elastic Stack is used to ingest, store, search, and visualise data at scale. Elasticsearch is the distributed store/search engine, Kibana is the user interface, Logstash performs complex ingest/transform operations, and Elastic Agent provides a unified data collector. [Elastic Stack documentation](https://www.elastic.co/docs/get-started/the-stack)

### 1.1 Typical use cases

| Use case | Example |
|---|---|
| Centralised logging | Collect Apache, WebLogic, Oracle, Linux, and application logs in one place. |
| Troubleshooting | Find errors for a specific user request, host, application, or time window. |
| Security analytics | Detect suspicious login activity, denied access, or unexpected privilege changes. |
| Operational dashboards | Show error trends, request volumes, deployment events, and server health. |
| Audit evidence | Retain searchable records for a defined retention period. |
| Capacity / incident analysis | Correlate an increase in errors with a release, filesystem issue, or database event. |

## 2. High-level architecture and workflow

```text
Application / server logs
  (Apache, WebLogic, Oracle, Linux)
              │
              ▼
 Filebeat / Elastic Agent  ── secure transport ──>  Logstash (optional)
              │                                        │
              │                                        ├─ Parse, filter, enrich
              │                                        ▼
              └──────────────────────────────────> Elasticsearch
                                                        │
                                                        ├─ Data streams / indices
                                                        ├─ Search and aggregation
                                                        ▼
                                                     Kibana
                                              Discover / dashboards / alerts
```

### End-to-end event workflow

1. An application writes a log event, for example a WebLogic error to `server.log`.
2. Filebeat or Elastic Agent reads the new line and records its position so it does not resend previously acknowledged events after a restart.
3. The shipper sends the event over TLS to Logstash or directly to Elasticsearch.
4. Logstash, if used, parses the log line, adds fields such as environment/customer, masks sensitive data, and sends the enriched event to Elasticsearch.
5. Elasticsearch stores the event in a data stream or index, where it becomes searchable shortly after indexing.
6. Kibana lets an operator filter by time, hostname, log level, request ID, customer/environment, or error text.
7. Kibana/Elasticsearch alerting can create a notification when matching errors exceed an agreed threshold.

## 3. Elasticsearch

### 3.1 What Elasticsearch does

Elasticsearch is a distributed search and analytics engine. It receives documents—normally JSON records—indexes their fields, and provides near-real-time search, filtering, aggregation, and analytics through REST APIs.

It runs as a cluster of one or more nodes. Data is organised into indices, divided into shards, and can be replicated to other nodes for resilience. [Elastic Stack documentation](https://www.elastic.co/docs/get-started/the-stack)

### 3.2 Key Elasticsearch concepts

| Concept | Meaning | Example |
|---|---|---|
| Cluster | One or more Elasticsearch nodes working together. | `prod-logging-cluster` |
| Node | One Elasticsearch process/server in a cluster. | `es-data-01` |
| Index | Logical collection of similar JSON documents. | `logs-weblogic-2026.08.26` |
| Data stream | Time-series oriented collection backed by rolling indices. | `logs-system.auth-default` |
| Document | One JSON event stored in Elasticsearch. | One Apache access-log line. |
| Field | A named value within a document. | `log.level`, `host.name` |
| Mapping | Definition of field types and indexing behaviour. | `@timestamp` is a date field. |
| Shard | A partition of an index. | Primary shard 0 of an index. |
| Replica shard | Copy of a primary shard on another node. | Supports availability/search load. |
| Ingest pipeline | Processors that modify a document before it is indexed. | Parse JSON; add environment; redact values. |

### 3.3 Example log document

```json
{
  "@timestamp": "2026-08-26T09:31:42.712Z",
  "log.level": "ERROR",
  "message": "JDBC connection pool exhausted",
  "service.name": "leanapps-portal",
  "host.name": "accanlwlsl31",
  "environment": "acc",
  "customer.code": "anl",
  "event.dataset": "weblogic.server",
  "trace.id": "8c7a2a1df4",
  "labels": {
    "managed_server": "ManagedServer1"
  }
}
```

### 3.4 Elasticsearch REST API examples

> Use approved credentials and TLS in all real environments. The examples omit authentication only to keep the syntax clear.

Check cluster health:

```bash
curl -s http://localhost:9200/_cluster/health?pretty
```

List indices:

```bash
curl -s http://localhost:9200/_cat/indices?v
```

Search for ERROR events in ACC during the last hour:

```bash
curl -s -X POST 'http://localhost:9200/logs-*/_search?pretty' \
  -H 'Content-Type: application/json' \
  -d '{
    "size": 50,
    "query": {
      "bool": {
        "filter": [
          {"term": {"environment.keyword": "acc"}},
          {"term": {"log.level.keyword": "ERROR"}},
          {"range": {"@timestamp": {"gte": "now-1h"}}}
        ]
      }
    },
    "sort": [{"@timestamp": "desc"}]
  }'
```

### 3.5 Important field and mapping practices

- Use a consistent schema, preferably the **Elastic Common Schema (ECS)** where suitable.
- Store timestamps in UTC in `@timestamp`.
- Map identifiers intentionally: exact-match values usually need `keyword`; analysed full text needs `text`.
- Do not map every dynamic value automatically; uncontrolled dynamic fields can cause mapping explosion.
- Keep request IDs, session IDs, and customer identifiers searchable only when justified, protected, and compliant with privacy policy.
- Set the index/data-stream lifecycle before large-scale ingestion, not afterwards.

## 4. Logstash

### 4.1 What Logstash does

Logstash is a data collection and transformation engine. It processes events through a configurable pipeline of **inputs**, **filters**, and **outputs**. It is valuable when logs need complex parsing, enrichment, routing, masking, or fan-out to multiple destinations.

The Elastic documentation describes Logstash as a real-time data collection engine that unifies and normalises data from different sources through input, filter, output plugins, and codecs. [Elastic Stack documentation](https://www.elastic.co/docs/get-started/the-stack)

### 4.2 Logstash pipeline model

```text
Input → Codec → Filter(s) → Output
```

| Pipeline stage | Purpose | Example |
|---|---|---|
| Input | Receives events. | Beats, syslog, file, Kafka, HTTP. |
| Codec | Decodes/encodes event data. | JSON, multiline, plain text. |
| Filter | Parses, converts, enriches, removes, or redacts data. | Grok, date, mutate, dissect, geoip. |
| Output | Sends the final event somewhere. | Elasticsearch, file, Kafka, stdout. |

### 4.3 Example: Filebeat → Logstash → Elasticsearch

Create `/etc/logstash/conf.d/weblogic.conf`:

```conf
input {
  beats {
    port => 5044
    ssl_enabled => true
    ssl_certificate => "/etc/logstash/certs/logstash.crt"
    ssl_key => "/etc/logstash/certs/logstash.key"
  }
}

filter {
  if [event][dataset] == "weblogic.server" {
    grok {
      match => {
        "message" => "%{TIMESTAMP_ISO8601:weblogic.timestamp} %{LOGLEVEL:log.level} %{GREEDYDATA:message}"
      }
      tag_on_failure => ["_weblogic_grok_failure"]
    }

    date {
      match => ["weblogic.timestamp", "ISO8601"]
      target => "@timestamp"
    }

    mutate {
      add_field => {
        "environment" => "acc"
        "customer.code" => "anl"
        "service.name" => "leanapps-life"
      }
      remove_field => ["weblogic.timestamp"]
    }
  }

  # Example: mask a sensitive token if it appears in a message.
  mutate {
    gsub => ["message", "(?i)(authorization: bearer )[^ ]+", "\\1[REDACTED]"]
  }
}

output {
  elasticsearch {
    hosts => ["https://es-data-01.example.internal:9200"]
    ssl_enabled => true
    user => "${ES_WRITER_USER}"
    password => "${ES_WRITER_PASSWORD}"
    data_stream => "true"
    data_stream_type => "logs"
    data_stream_dataset => "weblogic.server"
    data_stream_namespace => "acc"
  }

  # Temporarily useful while building/testing a pipeline.
  stdout { codec => rubydebug }
}
```

Validate configuration before restarting the service:

```bash
sudo /usr/share/logstash/bin/logstash --path.settings /etc/logstash -t
sudo systemctl restart logstash
sudo systemctl status logstash --no-pager
```

### 4.4 When Logstash is appropriate

Use Logstash when you need one or more of the following:

- Receive data from multiple source types and protocols.
- Complex parsing of legacy unstructured logs with Grok/Dissect.
- Enrichment from a lookup source such as CMDB, GeoIP, or static mapping file.
- Data redaction/masking before logs leave a server boundary.
- Routing different events to separate data streams/indices or destinations.
- Persistent queues to absorb temporary downstream outages.

Avoid adding Logstash only because it is part of the ELK acronym. For straightforward logs, Elastic Agent/Filebeat can send directly to Elasticsearch, optionally using Elasticsearch ingest pipelines. This reduces components to operate.

## 5. Kibana

### 5.1 What Kibana does

Kibana is the web-based UI for exploring, managing, and visualising Elasticsearch data. It provides Discover for searching raw documents, Lens/visualisations for charts, dashboards, alerting, cases, Dev Tools Console, and data-management functions. [Elastic Stack documentation](https://www.elastic.co/docs/get-started/the-stack)

### 5.2 Common Kibana functions

| Function | Practical purpose |
|---|---|
| Discover | Search raw logs while investigating an incident. |
| Data views | Define index/data-stream patterns such as `logs-*` and select a timestamp field. |
| Lens | Build visualisations with drag-and-drop fields. |
| Dashboards | Combine graphs/tables for a service or environment. |
| Alerts | Create rules based on query counts, thresholds, or machine-learning conditions. |
| Cases | Track an incident/investigation and attach alerts/evidence. |
| Dev Tools Console | Run Elasticsearch API requests interactively. |
| Stack Management | Manage roles, index lifecycle, ingest pipelines, and data views. |

### 5.3 KQL examples in Kibana Discover

| Investigation | KQL example |
|---|---|
| WebLogic errors in ACC | `environment : "acc" and log.level : "ERROR"` |
| One host | `host.name : "accanlwlsl31"` |
| HTTP server errors | `http.response.status_code >= 500` |
| Specific JIRA/change reference | `message : "LPTAM-56034"` |
| JDBC pool problem | `message : "JDBC" and message : "pool"` |
| Exclude known harmless message | `not message : "health-check"` |

### 5.4 Useful dashboard design

Create dashboards around an operational question rather than around a tool.

| Dashboard | Suggested panels |
|---|---|
| Service overview | Log volume, error count, error percentage, active alerts, latest release, availability. |
| WebLogic health | ERROR/WARN logs by managed server, JVM/GC metrics, stuck-thread messages, deployment events. |
| Reverse proxy | Request rate, HTTP 4xx/5xx trend, top client sources, backend errors, TLS errors. |
| Oracle operations | ORA- errors, listener errors, backup outcome, Data Guard events, tablespace messages. |
| Security / audit | Failed logins, privilege changes, denied requests, access by source network. |

## 6. Beats and Elastic Agent

### 6.1 Filebeat

**Filebeat** is a lightweight log shipper. It tails files and sends events to Logstash or Elasticsearch. It is commonly used for Apache, application, WebLogic, Oracle, and Linux log files.

In newer Elastic Stack deployments, Elastic recommends **Elastic Agent** for most use cases. Beats remains relevant for existing estates and focused lightweight deployments. [Elastic Stack documentation](https://www.elastic.co/docs/get-started/the-stack)

### 6.2 Elastic Agent

Elastic Agent is a unified agent that can collect logs, metrics, uptime data, and security data under one host policy. With **Fleet**, policies and upgrades can be centrally managed through Kibana.

### 6.3 Filebeat configuration example

This example reads WebLogic and Apache logs, adds metadata, and forwards securely to Logstash.

```yaml
filebeat.inputs:
  - type: filestream
    id: weblogic-server-log
    enabled: true
    paths:
      - /opt/wl/domains/*/servers/*/logs/*.log
    fields:
      environment: acc
      customer.code: anl
      service.name: leanapps-life
      event.dataset: weblogic.server
    fields_under_root: true

  - type: filestream
    id: apache-access-log
    enabled: true
    paths:
      - /var/log/httpd/*access*.log
    fields:
      environment: acc
      customer.code: anl
      event.dataset: apache.access
    fields_under_root: true

processors:
  - add_host_metadata: ~
  - add_cloud_metadata: ~

output.logstash:
  hosts: ["logstash-01.example.internal:5044", "logstash-02.example.internal:5044"]
  ssl.enabled: true
  ssl.certificate_authorities: ["/etc/filebeat/certs/ca.crt"]

logging.level: info
logging.to_files: true
```

Validate and test Filebeat:

```bash
sudo filebeat test config
sudo filebeat test output
sudo systemctl restart filebeat
sudo journalctl -u filebeat -f
```

### 6.4 Multiline logs

Java stack traces span multiple lines. Without multiline configuration, each line may become a separate event, making troubleshooting hard.

Example for a log in which a new event begins with an ISO timestamp:

```yaml
parsers:
  - multiline:
      type: pattern
      pattern: '^\d{4}-\d{2}-\d{2}[ T]'
      negate: true
      match: after
```

Test multiline rules against real—but sanitised—log samples. A wrong rule can merge unrelated events or split a stack trace incorrectly.

## 7. Practical end-to-end example: WebLogic error investigation

### Scenario

Users report that a LeanApps Life portal operation is failing after a release. The application is behind an Apache reverse proxy and runs on a WebLogic managed-server cluster.

### Workflow

```text
User reports failure
       ↓
Kibana dashboard shows increase in 5xx / ERROR events
       ↓
Discover filters logs by time, service, and request/trace ID
       ↓
Correlate Apache proxy error with WebLogic exception
       ↓
Identify JDBC / deployment / backend root cause
       ↓
Apply approved remediation
       ↓
Verify error rate returns to baseline and document evidence
```

### Example search sequence

1. Set the Kibana time range to the incident window, for example **Last 30 minutes**.
2. In Discover, start broad:

```text
environment : "acc" and service.name : "leanapps-life"
```

3. Focus on failures:

```text
environment : "acc" and (log.level : "ERROR" or http.response.status_code >= 500)
```

4. Identify the source host and associated request identifier:

```text
host.name : "accanlwlsl31" and message : "JDBC"
```

5. Search Apache logs for the same time/request ID and compare response code, upstream host, and duration.
6. Check whether the issue appears on one managed server or across the cluster.
7. Correlate with release/maintenance annotations and deployment log events.
8. Export or retain the relevant search/dashboard evidence according to the incident process.

## 8. Data lifecycle and retention

Log platforms can grow very quickly. Data lifecycle management is required to control cost and keep search performance predictable.

### 8.1 Index Lifecycle Management (ILM)

An ILM policy can move data through lifecycle phases:

| Phase | Purpose | Example action |
|---|---|---|
| Hot | Recently indexed, frequently searched data. | Store on fast nodes; allow writes. |
| Warm | Less frequently searched data. | Move to lower-cost capacity. |
| Cold | Retained mainly for historical investigation. | Lower-cost searchable storage. |
| Frozen / archive strategy | Long-term retention with slower retrieval. | Use organisation-approved archival approach. |
| Delete | Data has reached retention expiry. | Delete automatically. |

### 8.2 Retention questions to answer before onboarding a log source

- What business, audit, security, or incident requirement justifies the data?
- Does it contain personal data, customer data, tokens, passwords, or document content?
- How long must it remain searchable online?
- Who may access it, and what role-based controls are required?
- How much data does it produce per day, including peak release/incident volume?
- Which fields must be parsed and searchable?
- Is data masking required at the agent, Logstash, ingest-pipeline, or application layer?

## 9. Security and operational best practices

### 9.1 Security

- Enable TLS for every connection: shipper → Logstash, shipper/Logstash → Elasticsearch, user → Kibana, and node-to-node Elasticsearch traffic.
- Use named users, API keys/service accounts, and least-privilege roles. Never use an administrative account for Filebeat or Logstash writing.
- Restrict network access: do not expose Elasticsearch transport/API ports or Logstash Beats ports to the public internet.
- Use RBAC in Kibana and separate access by environment/customer where required.
- Redact secrets and sensitive customer data before indexing. Once indexed, data may be replicated, backed up, and exposed in multiple views.
- Protect snapshots, backups, and exported dashboards as carefully as the live cluster.
- Patch Elastic components together according to supported version compatibility; Elastic documentation states that stack products should use the same version. [Elastic Stack documentation](https://www.elastic.co/docs/get-started/the-stack)

### 9.2 Operations

- Use at least three appropriately designed Elasticsearch nodes for a resilient production cluster; validate topology against vendor sizing/production guidance.
- Monitor cluster health, disk watermarks, JVM heap, indexing failures, shard allocation, ingestion lag, and Logstash queue capacity.
- Avoid a large number of tiny indices/shards; shard count has material memory and operational cost.
- Use snapshots to an approved repository and test restore procedures.
- Manage Filebeat/Agent policies, Logstash pipelines, ILM policies, and Kibana saved objects as version-controlled configuration.
- Test parsers with representative sanitised logs before broad rollout.
- Plan maintenance windows and rolling upgrade procedures; do not upgrade every component simultaneously without rollback validation.
- Elastic’s production guidance highlights resilience, performance, fault tolerance, replication, and workload distribution as key considerations. [Elastic production guidance](https://www.elastic.co/docs/deploy-manage/production-guidance)

## 10. Troubleshooting reference

| Symptom | Checks |
|---|---|
| Filebeat cannot send logs | `filebeat test output`; DNS; TCP/TLS connectivity; certificate trust; shipper credentials; Logstash listener. |
| Logs missing from Kibana | File path/permissions; Filebeat registry; Filebeat logs; Logstash pipeline; Elasticsearch index/data stream; Kibana time range/data view. |
| Logstash pipeline fails | `logstash -t`; service logs; plugin compatibility; Grok pattern; field types; Elasticsearch credentials. |
| `_grokparsefailure` tag | Inspect raw message; make timestamp/pattern more accurate; avoid overly broad greedy patterns. |
| Elasticsearch is yellow/red | `_cluster/health`; unassigned shards; disk capacity; node availability; allocation settings. |
| High disk consumption | Check data volume, retention/ILM, shard count, snapshot state, mapping explosion, and duplicate ingestion. |
| Kibana search slow | Narrow time range/fields; check shard/cluster performance; avoid wildcard-heavy queries; review index design. |
| Duplicate events | Review file identity/rotation configuration, shipper registry state, upstream retries, and pipeline output retries. |

Useful checks:

```bash
# Filebeat
sudo filebeat test config
sudo filebeat test output
sudo journalctl -u filebeat -n 100 --no-pager

# Logstash
sudo /usr/share/logstash/bin/logstash --path.settings /etc/logstash -t
sudo journalctl -u logstash -n 100 --no-pager

# Elasticsearch (authentication omitted for clarity)
curl -s http://localhost:9200/_cluster/health?pretty
curl -s http://localhost:9200/_cat/nodes?v
curl -s http://localhost:9200/_cat/indices?v
```

## 11. ELK versus Prometheus/Grafana

| Area | ELK / Elastic Stack | Prometheus + Grafana |
|---|---|---|
| Main strength | Search and analysis of logs/events. | Numeric time-series metrics and monitoring. |
| Data style | Rich, often high-volume JSON/text documents. | Numeric measurements with labels. |
| Typical question | “Show all WebLogic errors around 10:15 on ACC.” | “What was CPU, error rate, or latency over the last hour?” |
| Collection | Agents/Beats/Elastic Agent, Logstash, ingest pipelines. | Pull scrapes from exporters/application endpoints. |
| Visualisation | Kibana. | Grafana (and Prometheus expression UI). |
| Best practice | Use together when possible: metrics show the symptom; logs explain the cause. | Use together when possible: metrics show the symptom; logs explain the cause. |

Example correlation: Prometheus/Grafana alerts that HTTP 5xx rate is high; Kibana then identifies the WebLogic exception, affected managed server, request ID, and database message causing it.
