# Day 18 – Detailed Helm Notes
## Date: 18-Aug-2026

## 1. What is Helm?

Helm is a package manager for Kubernetes. It packages Kubernetes resources into reusable **Charts** and manages deployed instances of those charts as **Releases**.

Without Helm, an application may require many YAML files:

```text
Deployment
Service
ConfigMap
Secret
Ingress
HPA
```

Helm lets us use templates and configuration values instead of maintaining separate duplicated YAML files for every environment.

```text
Helm Chart
   |
   +-- Chart.yaml
   +-- values.yaml
   +-- templates/
   |
   v
Rendered Kubernetes YAML
   |
   v
Kubernetes / EKS
```

---

# 2. Why Helm?

Without Helm:

```text
deployment-dev.yaml
deployment-stage.yaml
deployment-prod.yaml
service-dev.yaml
service-stage.yaml
service-prod.yaml
```

With Helm:

```text
myapp/
├── Chart.yaml
├── values.yaml
└── templates/
    ├── deployment.yaml
    ├── service.yaml
    └── _helpers.tpl
```

Environment-specific files can then provide different configuration:

```text
values-dev.yaml
values-stage.yaml
values-prod.yaml
```

The main benefit is:

> **One reusable chart + environment-specific configuration.**

---

# 3. Important Helm Terminology

## Chart

A package containing Kubernetes application definitions.

```text
myapp/
├── Chart.yaml
├── values.yaml
└── templates/
```

## Release

A deployed instance of a Helm Chart.

```bash
helm install myapp ./myapp
```

Here:

```text
Chart   = ./myapp
Release = myapp
```

The same chart can create several releases:

```text
myapp-dev
myapp-stage
myapp-prod
```

## Repository

A location from which Helm charts can be discovered and downloaded.

Example:

```bash
helm repo add bitnami https://charts.bitnami.com/bitnami
helm repo update
```

# 4. Helm Chart Structure

A typical chart:

```text
myapp/
├── Chart.yaml
├── values.yaml
├── charts/
└── templates/
    ├── deployment.yaml
    ├── service.yaml
    ├── ingress.yaml
    ├── serviceaccount.yaml
    ├── _helpers.tpl
    └── tests/
```

Important components:

| File/Directory | Purpose |
|---|---|
| `Chart.yaml` | Chart metadata |
| `values.yaml` | Default configuration |
| `templates/` | Kubernetes manifest templates |
| `_helpers.tpl` | Reusable template helpers |
| `charts/` | Chart dependencies |

# 6. Chart.yaml

Example:

```yaml
apiVersion: v2
name: myapp
description: A Helm chart for my application
type: application

appVersion: "1.0"
```

Important fields:

| Field | Meaning |
|---|---|
| `apiVersion` | Helm chart API version |
| `name` | Chart name |
| `description` | Description |
| `type` | `application` or `library` |
| `version` | Chart version |
| `appVersion` | Application version |

---

# 7. Chart Version vs Application Version

These are different.

```yaml
version: 1.2.0
appVersion: "3.5.0"
```

means:

```text
Chart version       = 1.2.0
Application version = 3.5.0
```

The chart can change without changing the application.

For example:

```text
Application = 3.5
Chart       = 1.4
```

Later, a template or configuration change may result in:

```text
Application = 3.5
Chart       = 1.5
```

---

# 8. values.yaml

`values.yaml` contains default configuration.

Example:

```yaml
replicaCount: 2

image:
  repository: nginx
  tag: "1.27"
  pullPolicy: IfNotPresent

service:
  type: ClusterIP
  port: 80
```

A template can reference these values:

```yaml
replicas: {{ .Values.replicaCount }}
```

If:

```yaml
replicaCount: 2
```

the rendered YAML contains:

```yaml
replicas: 2
```

---

# 9. templates/

The `templates/` directory contains Kubernetes manifest templates.

Examples:

```text
deployment.yaml
service.yaml
ingress.yaml
configmap.yaml
serviceaccount.yaml
_helpers.tpl
```

Instead of:

```yaml
replicas: 3
```

use:

```yaml
replicas: {{ .Values.replicaCount }}
```

This makes the chart reusable.

---

# 10. Helm Template Syntax

Helm uses Go templates.

Basic expression:

```yaml
{{ .Values.replicaCount }}
```

Example:

```yaml
spec:
  replicas: {{ .Values.replicaCount }}
```

Nested values:

```yaml
image:
  repository: nginx
  tag: "1.27"
```

Template:

```yaml
image: "{{ .Values.image.repository }}:{{ .Values.image.tag }}"
```

Common objects:

```text

.Release
.Chart
.Capabilities
.Files
.Template
```

## `.Values`

Access values from `values.yaml`.

```yaml
{{ .Values.replicaCount }}
```

## `.Release`

Provides information about the current release.

```yaml
{{ .Release.Name }}
{{ .Release.Namespace }}
{{ .Release.IsInstall }}
{{ .Release.IsUpgrade }}
```

## `.Chart`

Provides chart metadata.

```yaml
{{ .Chart.Name }}
{{ .Chart.Version }}
{{ .Chart.AppVersion }}
```

# 12. Helm Helpers

`_helpers.tpl` defines reusable named templates.

Example:

```yaml
{{- define "myapp.name" -}}
{{- default .Chart.Name .Values.nameOverride | trunc 63 | trimSuffix "-" }}
{{- end }}
```

Use it:

```yaml
name: {{ include "myapp.name" . }}
```

Benefits:

```text
Reusability
Consistency
Cleaner templates
Centralized naming
```

---

# 13. Conditionals

Helm supports `if` conditions.

Example:

```yaml
{{- if .Values.ingress.enabled }}
apiVersion: networking.k8s.io/v1
kind: Ingress
...
{{- end }}
```

When:

```yaml
ingress:
  enabled: true
```

the Ingress is rendered.

When:

```yaml
ingress:
  enabled: false
```

it is not rendered.

---

# 14. if / else

Example:

```yaml
{{- if eq .Values.environment "prod" }}
replicas: 5
{{- else }}
replicas: 1
{{- end }}
```

---

# 15. Loops with range

Example values:

```yaml
ports:
  - 80
  - 443
  - 8080
```

Template:

```yaml
{{- range .Values.ports }}
- port: {{ . }}
{{- end }}
```

`range` is useful when generating repeated YAML structures.

---

# 16. range with Key/Value

Values:

```yaml
env:
  APP_NAME: myapp
  ENVIRONMENT: production
```

Template:

```yaml
{{- range $key, $value := .Values.env }}
- name: {{ $key }}
  value: {{ $value | quote }}
{{- end }}
```

---

# 17. default Function

Example:

```yaml
replicas: {{ default 1 .Values.replicaCount }}
```

If `replicaCount` is not supplied, Helm uses:

```text
1
```

Good charts should provide sensible defaults.

---

# 18. required Function

The `required` function forces a value to be supplied.

Example:

```yaml
image:
  repository: {{ required "image.repository is required" .Values.image.repository }}
```

This can prevent incomplete deployments.

---

# 19. quote Function

Example:

```yaml
value: {{ .Values.appName | quote }}
```

Output:

```yaml
value: "myapp"
```

This is useful when values should explicitly be treated as strings.

# 26. helm upgrade --install

A very useful deployment command:

```bash
helm upgrade --install myapp ./myapp
```

It means:

```text
Release exists?
       |
   +---+---+
   |       |
  Yes      No
   |       |
Upgrade   Install
```

This pattern is especially useful in CI/CD pipelines.

---

# 27. Release Revisions

A release gets revisions as it changes.

Example:

```text
Revision 1 → Initial install
Revision 2 → Upgrade
Revision 3 → Upgrade
```

Check:

```bash
helm history myapp
```

Important:

```text
Chart version != Release revision
```

---

# 28. Helm Rollback

If revision 3 introduces a problem:

```bash
helm rollback myapp 2
```

Then:

```bash
helm status myapp
helm history myapp
```

Conceptually:

```text
Revision 1
     ↓
Revision 2
     ↓
Revision 3  ← Problem
     ↓
Rollback
     ↓
New release revision
```

A rollback creates a new release revision; it does not simply erase the release history.

---

# 29. `--set`

Override values from the command line:

```bash
helm upgrade myapp ./myapp   --set replicaCount=5
```

Nested:

```bash
helm upgrade myapp ./myapp   --set service.type=LoadBalancer
```

Multiple values:

```bash
helm upgrade myapp ./myapp   --set replicaCount=3   --set service.type=LoadBalancer
```

---

# 30. Values Precedence

Common sources:

```text
Chart values.yaml
       ↓
Additional values files
       ↓
--set
```

Example:

```bash
helm upgrade myapp ./myapp   -f values-prod.yaml   --set replicaCount=5
```

The `--set` value can override the corresponding value from the values file.

If multiple `-f` files are supplied, later files can override overlapping values from earlier files.

# 41. Helm vs kubectl

`kubectl` directly manages Kubernetes resources:

```bash
kubectl apply -f deployment.yaml
```

Helm manages packaged Kubernetes applications:

```bash
helm install myapp ./myapp
```

Comparison:

| kubectl | Helm |
|---|---|
| Direct Kubernetes resource management | Kubernetes package/release management |
| YAML manifests | Templates + values |
| No Helm release model | Release management |
| Manual configuration | Reusable configuration |
| Resource operations | Install, upgrade, rollback |

They are complementary.

# 42. Helm and Kubernetes

Helm does **not** replace Kubernetes.

```text
Kubernetes

Helm
→ Package manager and release-management tool for Kubernetes
```

Helm renders/manages Kubernetes resources through the Kubernetes API.

# 45. Helm Best Practices

## Reusability

Avoid hardcoding:

```yaml
replicas: 3
```

Prefer:

```yaml
replicas: {{ .Values.replicaCount }}
```

## Sensible Defaults

Provide useful defaults in `values.yaml`:

```yaml
replicaCount: 1
```

## Consistent Naming

Use `_helpers.tpl` for common naming logic.

## Labels

Use standard Kubernetes labels such as:

```yaml
app.kubernetes.io/name
app.kubernetes.io/instance
app.kubernetes.io/version
app.kubernetes.io/managed-by
helm.sh/chart
```

## Keep Templates Simple

Avoid excessive nested logic. Put configuration in values files and common logic in helpers.

## Version Control

Store charts and values files in Git.

# 47. Semantic Versioning

A common chart version format is:

```text
MAJOR.MINOR.PATCH
```

Example:

```text
1.4.2
```

Typical meaning:

```text
Major → Breaking changes
Minor → Backward-compatible features
Patch → Bug fixes
```

Example:

```text
1.0.0
1.1.0
1.1.1
2.0.0
```

Use your organization's versioning policy where applicable.

# 51. Interview Questions

### What is Helm?

Helm is a package manager for Kubernetes that packages Kubernetes resources into reusable charts and manages their releases.

### What is a Helm Chart?

A package containing Kubernetes templates, metadata, configuration values and optional dependencies.

### What is values.yaml?

It contains default configuration values consumed by Helm templates.

### What is Chart.yaml?

It contains chart metadata such as name, chart version and application version.

### What is a Helm Release?

A deployed instance of a Helm Chart.

### What is `_helpers.tpl`?

A template file used to define reusable named template snippets.

### What does `helm template` do?

It renders the chart into Kubernetes YAML without installing it.

### What does `helm lint` do?

It checks the chart for common structural and configuration problems.

### What does `helm upgrade` do?

It updates an existing Helm release.

### What does `helm rollback` do?

It returns a release to a previous revision.

### Chart version vs release revision?

Chart version identifies a version of the chart package. Release revision tracks changes to a particular deployed release.

### Can the same chart be used for dev and prod?

Yes. The same chart can use different values files such as:

```text
values-dev.yaml
values-stage.yaml
values-prod.yaml
```

### Is Helm a replacement for Kubernetes?

No. Helm packages and manages Kubernetes applications; Kubernetes remains the orchestration platform.

# 53. Day 18 Summary

Key concepts to remember:

- Helm is a Kubernetes package manager.
- A **Chart** packages a Kubernetes application.
- `Chart.yaml` contains chart metadata.
- `values.yaml` contains default configuration.
- `templates/` contains Kubernetes manifest templates.
- `_helpers.tpl` contains reusable template helpers.
- `.Values` accesses configuration.
- `.Release` provides release information.
- `.Chart` provides chart metadata.
- `if` provides conditional rendering.
- `range` provides loops.
- `default` provides fallback values.
- `required` validates mandatory values.
- `helm lint` validates a chart.
- `helm template` renders manifests without deployment.
- `helm install` creates a release.
- `helm upgrade` changes an existing release.
- `helm upgrade --install` installs or upgrades.
- `helm history` shows release revisions.
- `helm rollback` returns a release to an earlier revision.
- Dev/stage/prod values files allow environment-specific configuration.
- Chart version and release revision are different concepts.
- Helm complements Kubernetes; it does not replace Kubernetes.
- Good Helm charts should be reusable, consistent, maintainable and have sensible defaults.
