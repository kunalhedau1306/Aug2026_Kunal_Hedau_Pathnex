# Site Reliability Engineering (SRE) — Detailed Notes

**Date:** 29-Aug-2026  
**Topics:** SRE, SLI/SLO/SLA, error budgets, SRE roles, and Change Advisory Board (CAB).

---

## 1. What is SRE?

Site Reliability Engineering applies software-engineering practices to operating reliable services. It does not mean avoiding every incident or every change. It means delivering an agreed, measurable level of reliability while making change safe, repeatable, and sustainable.

SRE combines:

- measurable user-facing reliability targets;
- automation to reduce repetitive manual work;
- observability, alerting, incident response, and learning;
- resilience, capacity, and recovery engineering;
- risk-aware release and change management.

~~~mermaid
flowchart LR
  U[Users] --> S[Service]
  S --> O[Observability]
  O --> R[Reliability indicators]
  R --> D[Engineering and change decisions]
  D --> S
~~~

| Traditional operations focus | SRE focus |
|---|---|
| Keep systems running through manual procedures. | Engineer systems to be reliable and recoverable. |
| Measure ticket closure. | Measure user-facing service health and reliability. |
| Treat changes mainly as risk. | Make necessary changes safe through tests, automation, and controls. |
| Alert on infrastructure thresholds alone. | Alert on user impact and reliability objectives. |

## 2. SRE roles and responsibilities

| Area | SRE responsibility | LeanApps example |
|---|---|---|
| Reliability design | Identify failure modes and resilience requirements. | Define WebLogic cluster, Data Guard, RPX/FPX, and quorum behaviour. |
| Observability | Build actionable metrics, dashboards, logs, and traces. | Monitor RPX errors, WLS health, DB status, and batch latency. |
| Incident response | Detect, triage, mitigate, communicate, and learn. | Recover a service after RPX/WLS/DB impact and conduct a review. |
| Change reliability | Validate release readiness, rollback, and post-change evidence. | Review ACC → PRE → PRD deployment runbooks. |
| Automation | Reduce toil and human error. | Use Puppet, Ansible, WLST, and shell automation. |
| Capacity | Forecast compute, storage, throughput, and limits. | Size Oracle, WebLogic, and storage for policy growth. |
| Recovery/security | Engineer recoverability without compromising security. | Monitor certificate expiry; test backup/restore and failover. |

### Toil

Toil is manual, repetitive, automatable work with little lasting value. Repeated manual health checks, copying logs by hand, or identical unautomated certificate renewals are examples. SRE reduces toil so people can address the underlying reliability need.

## 3. SLI, SLO, and SLA

| Term | Meaning | Example |
|---|---|---|
| **SLI — Service Level Indicator** | A measured value describing service behaviour. | 99.94% successful HTTPS requests over 30 days. |
| **SLO — Service Level Objective** | Internal target for an SLI in a defined time window. | At least 99.95% availability in rolling 30 days. |
| **SLA — Service Level Agreement** | Formal customer/contract commitment, often with reporting/consequences. | 99.90% monthly availability; service credits may apply below it. |

~~~mermaid
flowchart LR
  M[Measure service] --> I[SLI: actual value]
  I --> O[SLO: internal target]
  O --> A[SLA: external commitment]
~~~

An SLO is normally stricter than its SLA. That gives the team time to react before a contractual target is breached.

## 4. Designing useful SLIs

An SLI should describe the user’s experience. CPU usage is valuable diagnostic data but it is rarely a direct user-facing SLI.

| Category | Example SLI | Source |
|---|---|---|
| Availability | Percentage of valid requests completed successfully. | RPX/load balancer, synthetic probe, application metric |
| Latency | Percentage of requests within response-time target. | Application/APM, proxy, Prometheus histogram |
| Correctness | Percentage of business transactions completed correctly. | Application events, reconciliation |
| Freshness | Age of data visible to users. | Kafka/ETL/replication metrics |
| Durability | Percentage of accepted records not lost. | Database/Kafka/restore validation |
| Throughput | Successful transactions per minute at expected peak. | Application metrics |

Availability calculation:

~~~text
Availability (%) = successful valid requests / total valid requests × 100
~~~

Define success explicitly. For example, decide whether an HTTP 4xx is an expected client error or evidence of a service defect. A technical HTTP 200 must not hide a failed business transaction.

For latency, use percentiles rather than averages:

~~~text
99% of valid portal requests complete in 2 seconds or less.
~~~

## 5. SLOs and error budgets

Example:

~~~text
SLI: successful authenticated portal requests
SLO: at least 99.95% successful during a rolling 30-day window
~~~

The permitted unreliability is the **error budget**:

~~~text
Error budget = 100% − SLO
~~~

| SLO | Allowed unavailability in 30 days |
|---|---:|
| 99.0% | 7 h 12 m |
| 99.9% | 43 m 12 s |
| 99.95% | 21 m 36 s |
| 99.99% | 4 m 19 s |

### Using the error budget

- **Budget healthy:** continue planned delivery and reliability work.
- **Budget burns too quickly:** investigate failures, improve safeguards, and prioritize remediation.
- **Budget exhausted:** restrict non-essential risky changes until reliability recovers; continue emergency and critical security work.

Error budgets give Delivery, TAM, development, and business teams a shared data-based way to balance reliability and delivery speed.

## 6. Example LAL SLOs

These targets are examples. The customer and service owner must agree final targets.

| Journey | SLI | Example SLO | Meaning |
|---|---|---|---|
| Portal availability | Successful synthetic login/check | ≥ 99.95% in 30 days | Covers DNS → LB/RPX → WLS → DB. |
| API availability | Successful valid LA web-service requests | ≥ 99.9% in 30 days | Define valid request and expected errors. |
| Portal latency | P95 authenticated response time | ≤ 2 seconds | Break down per endpoint when needed. |
| Batch execution | Critical daily batch by agreed cutoff | ≥ 99.5% scheduled runs | Measures business outcome. |
| Recoverability | Restore test within target | 100% quarterly test pass | Confirms backups are usable. |

Planned maintenance exclusion must be explicitly defined in the SLO/SLA. Report customer-visible maintenance transparently even when the contract excludes it from the calculation.

## 7. SLO-based alerting

An alert should tell an on-call engineer that action is required now. Dashboards can provide broad diagnostic information; alerts should remain few and actionable.

**Burn rate** measures how fast the error budget is used:

~~~text
Burn rate = observed error rate / permitted error rate
~~~

For a 99.9% SLO, the permitted error rate is 0.1%. An actual 1% error rate consumes the budget at 10 times the expected rate.

| Signal | Response |
|---|---|
| Fast, high burn in short window | Page/on-call action; user impact likely immediate. |
| Slow sustained burn | Investigation/ticket; avoid later breach. |
| Single infrastructure threshold | Diagnose or alert only if it threatens service behaviour. |

This reduces alert fatigue from warnings that do not yet affect users.

## 8. Incident management and learning

~~~mermaid
flowchart LR
  D[Detect] --> T[Triage]
  T --> M[Mitigate impact]
  M --> C[Communicate]
  C --> R[Recover and validate]
  R --> P[Post-incident review]
  P --> A[Actions completed]
~~~

During an incident:

1. Assign an incident lead and communication channel.
2. Confirm user impact, scope, start time, and affected journeys.
3. Stabilize first: rollback, fail over, scale, isolate, or use approved workaround.
4. Communicate factual updates at an agreed cadence.
5. Preserve logs, metrics, timestamps, and recent-change evidence.
6. Validate recovery from the user’s perspective.

Post-incident reviews should be blameless. Record what happened, detection gaps, what helped, actions to prevent recurrence, owners, and due dates.

## 9. CAB: role and importance

The Change Advisory Board (CAB) assesses and coordinates changes that can materially affect services, customers, security, compliance, or shared infrastructure.

| CAB participant | Contribution |
|---|---|
| Change manager | Process, records, agenda, decision governance. |
| Service owner/business representative | Customer impact and acceptable downtime. |
| TAM/operations/SRE | Operability, monitoring, support, and rollback. |
| Delivery/development | Scope, tested artefacts, dependencies, implementation. |
| Platform/network/DB teams | Shared component, capacity, and technical impact. |
| Security/compliance | Data, vulnerability, security, and regulatory impact. |

CAB evaluates business reason, dependencies, risk, test evidence, implementation steps, monitoring/success criteria, rollback, communications, schedule conflicts, and required approvals.

## 10. CAB is not a slowdown mechanism

SRE, DevOps, ITIL change enablement, and CAB complement each other:

| Practice | Primary contribution |
|---|---|
| DevOps | Collaboration, delivery automation, feedback loops, shared ownership. |
| SRE | Reliability targets, error budgets, observability, and engineering discipline. |
| ITIL change enablement | Risk-aware, auditable control of changes. |
| CAB | Cross-functional coordination for significant changes. |

The desired model is proportionate control: proven low-risk automated changes should flow fast, while high-risk or cross-service changes receive deeper review.

| Change type | Characteristics | CAB involvement |
|---|---|---|
| Standard | Pre-approved, repeatable, low-risk, documented and proven. | Template/control; normally no full review each time. |
| Normal | Assessed and scheduled before implementation. | CAB or delegated approval based on risk. |
| Emergency | Urgently restores service or remediates serious risk. | Emergency authorization, then retrospective review. |

Examples: a proven automated certificate renewal may become standard; an Oracle patch or WebLogic upgrade affecting a customer is typically a normal change; mitigation of a critical active vulnerability may require emergency control.

## 11. Change record quality checklist

| Section | Required content |
|---|---|
| Purpose | Reason and expected outcome. |
| Scope | Environments, servers, apps, DB/network dependencies. |
| Risk | Customer impact, failure modes, mitigations. |
| Implementation | Ordered steps, automation version, responsible people. |
| Validation | Technical and business tests, expected evidence. |
| Monitoring | Dashboards, logs, alerts, observation period. |
| Rollback | Trigger, exact steps, timing, decision owner, limitations. |
| Communication | Stakeholders, outage notice, completion update. |
| Schedule | Window, conflict check, resource availability. |

“Rollback available” is not enough. The record must state when to roll back, who decides, and whether rollback fits in the maintenance window.

## 12. Practical release workflow

~~~mermaid
flowchart TD
  P[Plan and assess] --> T[Test lower environments]
  T --> R[Runbook, validation and rollback ready]
  R --> C[CAB or delegated approval]
  C --> I[Implement]
  I --> V[Validate user journeys and SLO signals]
  V --> O[Observe and close with evidence]
  O --> L[Record improvement actions]
~~~

For LeanApps releases, Delivery prepares artefacts and runbooks while TAM deploys through ACC and PRE before PRD. SRE strengthens this process with user-journey success criteria and active post-change SLO observation.

## 13. Anti-patterns

| Anti-pattern | Why it fails | Better approach |
|---|---|---|
| 100% availability target | Often unrealistic and blocks useful change. | Agree business-appropriate SLO/error budget. |
| Server uptime only | Server can be up while users cannot complete work. | Measure end-to-end successful requests/transactions. |
| Alert every threshold | Noise and alert fatigue. | Alert on impact and burn rate; keep diagnostics on dashboards. |
| CAB as paperwork gate | Delays work without reducing risk. | Evidence-based, risk-proportionate review. |
| Same process for all changes | Teams bypass slow controls. | Standard, normal, emergency paths. |
| No post-change validation | Success assumed, not proven. | Define measurable technical/business checks. |
| Blame-focused reviews | Suppresses learning. | Blameless review with owned improvements. |

## 14. Key takeaways

1. SRE engineers reliable services through measurement, automation, observability, and learning.
2. SLI is the measure, SLO is the internal target, and SLA is the external commitment.
3. Error budgets align reliability and delivery decisions.
4. Good SLIs measure user outcomes rather than only component health.
5. CAB protects significant changes by coordinating risk, dependencies, validation, communication, and rollback.
6. Standard changes should be fast; high-risk changes deserve deeper review.
7. Reliability rises when improvements from incidents and changes are tracked to completion.

## 15. Suggested practice exercises

1. Define an SLI/SLO for one LeanApps journey: login, policy retrieval, API request, or critical batch.
2. Calculate 30-day error budgets for 99.9%, 99.95%, and 99.99% availability.
3. Review one alert and decide whether it shows user impact or belongs on a dashboard.
4. Add SLO observation and explicit rollback trigger to a release runbook.
5. Create a CAB checklist for a WebLogic or Oracle maintenance change.
