# 1. EKS + Jump Server Architecture

```text
                         Internet
                            |
                     +------+------+
                     | Jump Server |
                     | Bastion EC2 |
                     +------+------+
                            |
                         SSH 22
                            |
             +--------------+--------------+
             |                             |
       Private Worker 1              Private Worker 2
             |                             |
            Pods                          Pods

Administrator --kubectl--> EKS API Server
```

Important distinction:

```text
kubectl
  |
  +--> EKS Kubernetes API

SSH
  |
  +--> Jump Server
          |
          +--> Private EC2 Worker Node
```

A jump server is an administrative SSH entry point. It is not the Kubernetes control plane.

# 3. Jump/Bastion Server

A jump server is an EC2 instance placed in a public subnet and used to reach private servers.

Typical architecture:

```text
Internet
   |
Internet Gateway
   |
Public Subnet
   |
Jump Server
   |
Private Subnet
   |
+-- Worker Node 1
+-- Worker Node 2
```

Recommended security groups:

```text
Jump SG:
TCP 22 <-- trusted administrator IP

Worker SG:
TCP 22 <-- Jump Server Security Group
```

Avoid exposing worker SSH directly:

```text
Worker SG:
SSH 22 <-- 0.0.0.0/0   # Avoid
```

Connect to jump server:

```bash
ssh -i my-key.pem ec2-user@<jump-public-ip>
```

Then connect to a private worker:

```bash
ssh -i my-key.pem ec2-user@<worker-private-ip>
```

For production, alternatives such as AWS Systems Manager Session Manager can reduce the need for exposed SSH/bastion infrastructure.

## Important EKS point

A jump server is not automatically required to run:

```bash
kubectl get nodes
```

You need network reachability to the EKS API endpoint plus appropriate AWS/IAM/Kubernetes authorization. The jump server is mainly useful for administrative access to private EC2 worker nodes.

# 4. Kubernetes Namespaces

A Namespace logically divides a Kubernetes cluster.

```text
Cluster
 |
 +-- dev
 |    +-- Pods
 |    +-- Services
 |    +-- Deployments
 |
 +-- test
 |
 +-- prod
```

Namespaces can help with:

- Environment separation
- Team/application organization
- RBAC
- Resource quotas
- Network policies

Kubernetes starts with four initial namespaces. citeturn0search4turn0search6

List namespaces:

```bash
kubectl get namespaces
kubectl get ns
```

# 5. Default Kubernetes Namespaces

## default

The `default` namespace is used when you do not specify another namespace.

```bash
kubectl get pods
```

is normally querying the current/default namespace.

---

## kube-system

Used for Kubernetes/system infrastructure components.

Check:

```bash
kubectl get pods -n kube-system
```

You may see components such as:

```text
CoreDNS
kube-proxy
CNI components
EKS add-on components
```

Avoid casually deleting resources from this namespace.

---

## kube-public

Created automatically and readable by all clients, including unauthenticated clients, according to Kubernetes documentation.

It is intended for information that may need to be publicly readable within the cluster. citeturn0search6

---

## kube-node-lease

Contains Lease objects associated with nodes.

```text
Worker Node
    |
  kubelet
    |
 Node Lease / heartbeat
    |
 kube-node-lease
```

These leases help the control plane detect node failures. citeturn0search4

# 7. Kubernetes Service

Pods are temporary and their IP addresses can change.

A Service gives clients a stable endpoint and selects backend Pods.

```text
             Service
                |
       +--------+--------+
       |        |        |
     Pod 1    Pod 2    Pod 3
```

Kubernetes has four primary Service types:

```text
ClusterIP
NodePort
LoadBalancer
ExternalName
```

citeturn0search2turn0search3

---

# 8. ClusterIP

Default Service type.

Accessible from within the cluster.

```text
Internal Client
      |
      v
 ClusterIP
      |
 +----+----+
 |    |    |
Pod  Pod  Pod
```

Example:

```bash
kubectl expose deployment nginx \
  --port=80 \
  --type=ClusterIP
```

Use it for internal applications and microservice-to-microservice communication.

---

# 9. NodePort

Exposes a Service on a port on each Kubernetes node.

```text
Client
  |
  | NodeIP:NodePort
  v
Worker Node
  |
Service
  |
Pods
```

Example:

```bash
kubectl expose deployment nginx \
  --port=80 \
  --type=NodePort
```

Check:

```bash
kubectl get svc
```

Typical output:

```text
80:30xxx/TCP
```

Use cases:

- Simple testing
- Development
- Situations where node-level exposure is appropriate

# 11. ExternalName

Maps a Kubernetes Service name to an external DNS name.

Example:

```yaml
apiVersion: v1
kind: Service
metadata:
  name: external-api
spec:
  type: ExternalName
  externalName: api.example.com
```

It works through DNS and does not proxy traffic itself. citeturn0search2

# 12. Service Type Summary

| Type | Access | Typical use |
|---|---|---|
| ClusterIP | Internal cluster | Internal services |
| NodePort | Node IP + port | Testing/simple exposure |
| LoadBalancer | External cloud LB | External applications |
| ExternalName | DNS alias | External services |

# 13. Network Load Balancer (NLB)

AWS NLB operates primarily at:

```text
Layer 4 – Transport
```

Common workloads:

```text
TCP
UDP
TLS
```

Use NLB when:

- TCP/UDP is required
- L4 load balancing is required
- Client source IP preservation is important
- Static IP use cases matter

AWS EKS documentation recommends NLB for TCP/UDP and source-IP-preservation requirements. citeturn0search0turn0search1

Example:

```text
Client
  |
TCP/UDP
  |
 NLB
  |
Service / Pods
```

---

# 14. Application Load Balancer (ALB)

ALB operates at:

```text
Layer 7 – Application
```

It understands HTTP/HTTPS.

It can route based on application-level information such as:

```text
Host
Path
HTTP headers
Query string
```

Example:

```text
example.com/api
       |
       v
      ALB
       |
       +-- /api --> API Service
       |
       +-- /web --> Web Service
```

In EKS, an Ingress used with the AWS Load Balancer Controller can provision an ALB. citeturn0search0

---

# 15. NLB vs ALB

| Feature | NLB | ALB |
|---|---|---|
| Layer | L4 | L7 |
| Main protocols | TCP/UDP/TLS | HTTP/HTTPS |
| HTTP-aware | No | Yes |
| Path routing | No | Yes |
| Host routing | No | Yes |
| Source IP preservation use case | Strong | Different model |
| Static IP use case | Strong | Usually DNS-based |
| EKS resource commonly used | Service `LoadBalancer` | Ingress |
| Best for | TCP/UDP | Web/API traffic |

Easy memory trick:

```text
NLB = Network = Layer 4
ALB = Application = Layer 7
```

# 16. Kubernetes Deployment

A Deployment manages replicated application Pods and their updates.

Architecture:

```text
Deployment
    |
 ReplicaSet
    |
 +--+--+--+
 |  |  |  |
Pod Pod Pod
```

A Deployment provides:

- Desired replica count
- Pod replacement
- Rolling updates
- Rollbacks
- Version management

---

# 17. Create a Deployment

```bash
kubectl create deployment nginx \
  --image=nginx
```

Check:

```bash
kubectl get deployments
kubectl get rs
kubectl get pods
```

Create three replicas:

```bash
kubectl create deployment nginx \
  --image=nginx \
  --replicas=3
```

---

# 18. Deployment YAML

```yaml
apiVersion: apps/v1
kind: Deployment

metadata:
  name: nginx-deployment

spec:
  replicas: 3

  selector:
    matchLabels:
      app: nginx

  template:
    metadata:
      labels:
        app: nginx

    spec:
      containers:
        - name: nginx
          image: nginx:latest
          ports:
            - containerPort: 80
```

Apply:

```bash
kubectl apply -f nginx-deployment.yaml
```

# 19. Deployment → ReplicaSet → Pods

```text
Deployment
     |
     v
ReplicaSet
     |
 +---+---+---+
 |   |   |   |
Pod Pod Pod Pod
```

With:

```yaml
replicas: 3
```

the desired state is three Pods.

If one fails:

```text
Before:
Pod 1
Pod 2
Pod 3

Pod 2 fails

After reconciliation:
Pod 1
Pod 3
Pod 4
```

# 21. Rolling Update

Current image:

```text
nginx:1.25
```

Change image:

```bash
kubectl set image deployment/nginx \
  nginx=nginx:1.26
```

Check rollout:

```bash
kubectl rollout status deployment/nginx
```

Check history:

```bash
kubectl rollout history deployment/nginx
```

Kubernetes progressively replaces old Pods according to the Deployment rollout strategy.

---

# 22. Rollback

If the new release has a problem:

```bash
kubectl rollout undo deployment/nginx
```

Check:

```bash
kubectl rollout status deployment/nginx
```

# 29. Important Interview Questions

## Namespaces

**Q: What is a Namespace?**

A logical boundary for organizing and managing Kubernetes resources.

**Q: What are the four initial namespaces?**

```text
default
kube-system
kube-public
kube-node-lease
```

**Q: What is kube-system?**

It contains Kubernetes/system infrastructure workloads.

**Q: What is kube-node-lease?**

It contains node Lease objects used for kubelet heartbeats and node health detection.

---

## Services

**Q: What are the Service types?**

```text
ClusterIP
NodePort
LoadBalancer
ExternalName
```

**Q: Which is the default?**

```text
ClusterIP
```

**Q: Why do we need a Service?**

Because Pod IPs are ephemeral. A Service provides a stable endpoint and routes traffic to selected Pods.

---

## NLB vs ALB

**Q: Major difference?**

```text
NLB → Layer 4
ALB → Layer 7
```

**Q: When do you use NLB?**

TCP/UDP workloads, L4 traffic, or source-IP-preservation requirements.

**Q: When do you use ALB?**

HTTP/HTTPS applications requiring application-aware routing.

**Q: Which Kubernetes resource commonly provisions an ALB in EKS?**

An Ingress when used with the AWS Load Balancer Controller. citeturn0search0

---

## Deployments

**Q: What is a Deployment?**

A Kubernetes object that manages replicated application Pods and their updates.

**Q: Deployment vs ReplicaSet?**

```text
Deployment
   ↓
Manages rollout/version/desired state

ReplicaSet
   ↓
Maintains desired Pod count
```

**Q: How do you scale?**

```bash
kubectl scale deployment nginx --replicas=5
```

**Q: How do you update the image?**

```bash
kubectl set image deployment/nginx \
  nginx=nginx:1.26
```

**Q: How do you rollback?**

```bash
kubectl rollout undo deployment/nginx
```

## Key Takeaways

1. A jump server is an administrative entry point to private EC2 instances.
2. `kubectl` access to EKS and SSH access to worker EC2 nodes are different paths.
3. Kubernetes starts with four initial namespaces.
4. `ClusterIP` is the default Service type.
5. `NodePort` exposes a Service on node ports.
6. `LoadBalancer` requests an external cloud load balancer.
7. `ExternalName` provides a DNS alias.
8. NLB is Layer 4; ALB is Layer 7.
9. ALB is commonly used with EKS Ingress for HTTP/HTTPS routing.
10. Deployments manage replicated Pods and rolling updates.
11. ReplicaSets maintain the desired number of Pods.
12. Services provide stable access to changing Pod IPs.
