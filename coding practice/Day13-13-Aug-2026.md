# 2. Kubernetes Versioning

Kubernetes versions follow:

```text
MAJOR.MINOR.PATCH
```

Example:

```text
1.36.2
```

- `1` = major version
- `36` = minor version
- `2` = patch version

Examples of minor versions:

```text
1.34
1.35
1.36
```

A minor release can introduce new features, API changes, deprecations, bug fixes, and security improvements.

A patch release such as:

```text
1.36.1 → 1.36.2
```

normally contains fixes within the same minor release.

# 3. Kubernetes Development and Release Lifecycle

A simplified feature lifecycle is:

```text
Feature Development
       |
       v
Alpha
       |
       v
Beta
       |
       v
Stable
       |
       v
Patch Releases
       |
       v
End of Support
```

Not every feature necessarily follows every stage exactly.

## Alpha

- Experimental
- May be disabled by default
- APIs may change
- Not recommended for production-critical workloads

## Beta

- More mature than Alpha
- More testing and wider use
- APIs are more stable
- Still requires compatibility testing

## Stable

- Production-ready
- Intended for long-term use
- Still subject to eventual deprecation and removal

# 5. Amazon EKS Support Lifecycle

Amazon EKS provides:

```text
Standard Support
       |
       v
Extended Support
       |
       v
Automatic Upgrade
```

An EKS Kubernetes minor version receives:

- **14 months of Standard Support**
- **12 additional months of Extended Support**

Therefore, a version can have approximately:

```text
14 + 12 = 26 months
```

of EKS support. citeturn0search1turn0search2

# 7. Standard vs Extended Support

## Standard Support

During Standard Support:

- The version is normally supported by AWS.
- Applicable security fixes are provided.
- Normal EKS lifecycle support applies.

## Extended Support

Extended Support allows an EKS cluster to remain on the same minor version for another 12 months.

However:

- It costs more.
- It should be considered extra planning time, not a permanent strategy.
- You should still upgrade before the extended period ends.

AWS documents `STANDARD` and `EXTENDED` as the two EKS upgrade-policy options. citeturn0search4

# 8. What Happens if We Don't Upgrade?

Example:

```text
Cluster Version = 1.34
```

When Standard Support ends:

```text
1.34
 |
 +-- Standard Support
 |
 +-- Extended Support
 |
 +-- End of Extended Support
 |
 +-- Automatic Control Plane Upgrade
```

At the end of the full EKS lifecycle, AWS automatically upgrades the control plane to the oldest currently supported version through a gradual process.

Ordinary EKS Managed Node Groups and self-managed nodes are not automatically upgraded with that control-plane upgrade; they require their own upgrade process. citeturn0search2

# 9. Why Automatic Upgrade Can Be Risky

Automatic upgrades can expose compatibility problems:

- Deprecated APIs
- Removed APIs
- Old Helm charts
- Incompatible admission webhooks
- Incompatible CRDs
- Incompatible CSI/CNI components
- Networking changes
- Storage changes
- Application compatibility problems

Example:

```text
Application
    |
Old Kubernetes API
    |
Automatic Cluster Upgrade
    |
API removed
    |
Application may fail
```

Therefore:

> **Proactive upgrades are preferable to waiting for automatic upgrades.**

AWS recommends creating upgrade runbooks and regularly upgrading clusters. citeturn0search5

# 10. Patch vs Minor Upgrade

## Patch upgrade

```text
1.36.1 → 1.36.2
```

Same minor version.

Usually lower risk.

## Minor upgrade

```text
1.35 → 1.36
```

Requires more testing because APIs, features, and component behavior may change.

---

# 11. Kubernetes Upgrade Rule

Do not skip minor versions in the normal Kubernetes upgrade path.

Correct:

```text
1.34 → 1.35 → 1.36
```

Avoid:

```text
1.34 → 1.36
```

The Kubernetes version-skew policy requires the kube-apiserver upgrade path not to skip minor versions. citeturn0search0

---

# 12. Version Skew

During a controlled upgrade, different Kubernetes components can temporarily run different versions.

Example:

```text
Control Plane = 1.36
Worker Node   = 1.35
```

Kubernetes defines supported version-skew limits.

For example, kubelet must not be newer than kube-apiserver and may be up to three minor versions older under the current policy. `kubectl` is supported within one minor version older or newer than kube-apiserver. citeturn0search0

Always verify the exact version-skew policy for your target version.

# 13. EKS Upgrade Order

A practical EKS upgrade flow is:

```text
Check Current Version
        ↓
Check Support Dates
        ↓
Review Release Notes
        ↓
Check Deprecated APIs
        ↓
Check Add-ons
        ↓
Backup / Recovery Validation
        ↓
Upgrade EKS Control Plane
        ↓
Upgrade EKS Add-ons
        ↓
Upgrade Worker Nodes
        ↓
Validate Applications
        ↓
Monitor
```

AWS manages the EKS control-plane upgrade after it is initiated, while customers are responsible for the data plane, add-ons, and workload validation. citeturn0search5

# 35. What Happens When a Worker Node Fails?

Suppose:

```text
Node 1
Node 2
Node 3
```

Node 2 fails.

Kubernetes detects the node problem.

If the application is managed by an appropriate controller:

```text
Node 2
  X
  |
  v
Workload becomes unavailable
  |
  v
Controller reconciles desired state
  |
  v
Workload recreated/rescheduled
on available capacity
```

Actual behavior depends on workload type, scheduling rules, storage, PodDisruptionBudgets, and application architecture.

# 42. Interview Questions

### 1. Why should Kubernetes be upgraded?

For security fixes, bug fixes, supported features, compatibility, and continued platform support.

### 2. Patch vs minor upgrade?

```text
1.36.1 → 1.36.2   # Patch
1.35   → 1.36     # Minor
```

### 3. Can we jump from 1.34 directly to 1.36?

Normally no. Use:

```text
1.34 → 1.35 → 1.36
```

### 4. What happens when EKS Standard Support ends?

Depending on upgrade policy:

```text
STANDARD
   ↓
Automatic upgrade after Standard Support

EXTENDED
   ↓
12 months additional support
   ↓
Additional cost
   ↓
Automatic upgrade at end of lifecycle
```

citeturn0search2turn0search4

### 5. Does an automatic EKS control-plane upgrade automatically upgrade ordinary worker nodes?

No. Ordinary EKS Managed Node Groups and self-managed nodes require their own upgrade process. citeturn0search2

### 6. What is a worker node?

A compute machine that runs Kubernetes Pods. In EKS it can commonly be an EC2 instance.

### 7. What is an EKS Managed Node Group?

An AWS-managed group of EC2 worker nodes attached to an EKS cluster.

### 8. How do you check worker nodes?

```bash
kubectl get nodes
```

### 9. How do you configure kubectl for EKS?

```bash
aws eks update-kubeconfig   --region <region>   --name <cluster-name>
```

### 10. What is the EKS upgrade order?

```text

      ↓

      ↓
```

## Key takeaways

1. Kubernetes minor releases and patch releases have different upgrade risks.
2. Do not skip minor Kubernetes versions in the normal upgrade path.
3. EKS provides 14 months of Standard Support plus 12 months of Extended Support.
4. Extended Support costs more.
5. Do not rely on automatic upgrades for production change management.
6. Review deprecated APIs before upgrading.
7. Upgrade the EKS control plane first.
8. Upgrade compatible EKS add-ons.
9. Upgrade worker nodes/data plane.
10. Validate applications after the upgrade.
11. `kubectl get nodes` is a key command for verifying worker nodes.
12. EKS Managed Node Groups are a convenient way to run EC2 worker nodes.
13. Clean up training resources after practice to avoid unnecessary AWS charges.
