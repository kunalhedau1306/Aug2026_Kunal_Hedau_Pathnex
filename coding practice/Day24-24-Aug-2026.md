## 1. Jenkins as an Automation Platform

Jenkins is an open-source automation server used for:

- Continuous Integration (CI)
- Continuous Delivery (CD)
- Continuous Deployment
- Build automation
- Testing
- Application deployment
- Infrastructure automation
- Scheduled jobs
- Pipeline orchestration

Typical workflow:

```text
Developer
   |
   v
GitHub / Bitbucket
   |
   | Webhook
   v
Jenkins
   |
   +---- Build
   +---- Unit Test
   +---- Security Scan
   +---- Docker Build
   +---- Push Image
   +---- Deploy
   |
   v
AWS / Kubernetes / Servers
```

Jenkins can therefore act as an automation and orchestration platform rather than only a CI tool.

## 2. Jenkins Job Types

### Freestyle Project

A traditional GUI-based Jenkins job.

```text
Jenkins UI
   |
   +-- Source Code
   +-- Build Steps
   +-- Post Build Actions
```

Freestyle jobs are useful for simple automation but become harder to maintain at enterprise scale.

### Pipeline

A Jenkins Pipeline defines the CI/CD workflow as code.

```text
Jenkinsfile
     |
     v
Jenkins
     |
     v
Pipeline execution
```

Pipeline is generally preferred for modern Jenkins implementations.

---

## 3. Jenkinsfile

A **Jenkinsfile** is a text file containing the Jenkins Pipeline definition. It is normally stored in the source-code repository.

Example:

```text
my-application/
├── src/
├── pom.xml
├── Dockerfile
└── Jenkinsfile
```

Example:

```groovy
pipeline {
    agent any

    stages {
        stage('Build') {
            steps {
                sh 'mvn clean package'
            }
        }

        stage('Test') {
            steps {
                sh 'mvn test'
            }
        }

        stage('Deploy') {
            steps {
                sh './deploy.sh'
            }
        }
    }
}
```

This approach is called **Pipeline as Code**.

### Benefits

- Version controlled
- Code reviewed
- Reusable
- Auditable
- Easier rollback
- Easier disaster recovery
- Changes tracked through Git

## 4. Declarative Pipeline

Declarative Pipeline uses a predefined and structured syntax.

```groovy
pipeline {

    agent any

    stages {

        stage('Build') {
            steps {
                sh 'mvn clean package'
            }
        }

        stage('Test') {
            steps {
                sh 'mvn test'
            }
        }

        stage('Deploy') {
            steps {
                sh './deploy.sh'
            }
        }
    }
}
```

Declarative Pipeline is generally easier to understand and is a good starting point for most teams.

### Important sections

```text
pipeline
   |
   +-- agent
   |
   +-- environment
   |
   +-- stages
   |     |
   |     +-- stage
   |           |
   |           +-- steps
   |
   +-- post
```

Example:

```groovy
pipeline {

    agent any

    environment {
        APP_NAME = 'myapp'
    }

    stages {
        stage('Build') {
            steps {
                echo 'Building application'
            }
        }

        stage('Test') {
            steps {
                echo 'Testing application'
            }
        }
    }

    post {
        success {
            echo 'Build successful'
        }

        failure {
            echo 'Build failed'
        }
    }
}
```

## 5. Scripted Pipeline

Scripted Pipeline uses Groovy-based programming constructs.

```groovy
node {

    stage('Build') {
        sh 'mvn clean package'
    }

    stage('Test') {
        sh 'mvn test'
    }

    stage('Deploy') {
        sh './deploy.sh'
    }
}
```

Scripted Pipeline provides greater programming flexibility.

---

## 6. Declarative vs Scripted

| Feature | Declarative | Scripted |
|---|---|---|
| Syntax | Structured | Groovy-based |
| Learning | Easier | More difficult |
| Flexibility | Controlled | Very flexible |
| Readability | High | Depends on code |
| Enterprise use | Very common | Used for advanced logic |
| Complex programming | More limited | Strong |
| Good starting point | Yes | After learning Declarative |

Simple rule:

```text
Simple/standard pipeline
        ↓
Declarative

Complex dynamic logic
        ↓
Scripted
```

## 7. Jenkins Agents

A Jenkins **agent** is a machine where Jenkins executes build and pipeline tasks.

Architecture:

```text
                 Jenkins Controller
                       |
          +------------+------------+
          |            |            |
          v            v            v
       Agent 1       Agent 2       Agent 3
        Linux        Docker        Windows
          |            |            |
        Java          Maven       .NET
```

The controller coordinates jobs while agents perform the workload.

### Why use agents?

- Distributed execution
- Scalability
- Workload isolation
- Different operating systems
- Different toolchains
- Better resource utilization

Avoid running heavy builds directly on the controller.

---

## 8. Agent Labels

Agents can have labels:

```text
linux
docker
windows
k8s
```

Example:

```groovy
pipeline {
    agent {
        label 'linux'
    }

    stages {
        stage('Build') {
            steps {
                sh 'mvn clean package'
            }
        }
    }
}
```

### `agent any`

```groovy
pipeline {
    agent any

    stages {
        stage('Build') {
            steps {
                echo 'Build running'
            }
        }
    }
}
```

Jenkins can use any suitable available agent.

### `agent none`

```groovy
pipeline {
    agent none

    stages {

        stage('Build') {
            agent {
                label 'linux'
            }

            steps {
                sh 'mvn clean package'
            }
        }

        stage('Test') {
            agent {
                label 'test'
            }

            steps {
                sh 'mvn test'
            }
        }
    }
}
```

This allows different stages to use different agents.

## 9. Jenkins Credentials Manager

Jenkins often needs credentials to communicate with:

- GitHub
- Bitbucket
- AWS
- Docker registries
- Kubernetes
- SSH servers
- Databases
- APIs

Jenkins Credentials Manager provides centralized management of secrets.

### Common credential types

```text
Username + Password
SSH Username + Private Key
Secret Text
Secret File
Certificate
API tokens
Cloud credentials
```

The exact available types depend on Jenkins and installed plugins.

---

## 10. Never Hard-Code Credentials

Bad:

```groovy
sh '''
    docker login       -u admin       -p MyPassword123
'''
```

Never put credentials in:

```text
Jenkinsfile
Git repository
Shell scripts
Dockerfiles
```

Instead, store them in Jenkins Credentials Manager.

Example:

```groovy
withCredentials([
    usernamePassword(
        credentialsId: 'docker-creds',
        usernameVariable: 'DOCKER_USER',
        passwordVariable: 'DOCKER_PASSWORD'
    )
]) {
    sh '''
        echo "$DOCKER_PASSWORD" |         docker login         -u "$DOCKER_USER"         --password-stdin
    '''
}
```

Flow:

```text
credentialsId
      ↓
Jenkins Credential
      ↓
Pipeline
      ↓
Environment variables
```

Never intentionally print secrets to the console.

## 11. Jenkins Webhooks

A webhook allows a Git system to notify Jenkins when an event occurs.

Without webhook:

```text
Jenkins
   |
   | Poll Git periodically
   v
Git Repository
```

With webhook:

```text
Developer
    |
    v
Git Push
    |
    v
GitHub / Bitbucket
    |
    | Webhook
    v
Jenkins
    |
    v
Pipeline
```

### Typical workflow

```text
Developer pushes code
        |
        v
Git Repository
        |
        | HTTP webhook
        v
Jenkins
        |
        v
Identify repository/branch
        |
        v
Checkout code
        |
        v
Run Jenkinsfile
        |
        v
Build → Test → Deploy
```

### Webhook vs Polling

Polling:

```text
Jenkins → Git → "Any changes?"
```

Webhook:

```text
Git → Jenkins → "Code changed!"
```

Webhooks are generally faster and avoid unnecessary periodic polling.

## 12. Jenkins Parallel Execution

Independent tasks can run simultaneously.

Sequential:

```text
Build
 ↓
Unit Test
 ↓
Security Scan
 ↓
Quality Scan
```

Parallel:

```text
             Build
               |
       +-------+-------+
       |       |       |
       v       v       v
    Unit     Security Quality
    Test      Scan     Scan
       |       |       |
       +-------+-------+
               |
               v
             Deploy
```

This can reduce pipeline execution time.

### Declarative parallel example

```groovy
pipeline {

    agent any

    stages {

        stage('Build') {
            steps {
                sh 'mvn clean package'
            }
        }

        stage('Parallel Validation') {

            parallel {

                stage('Unit Tests') {
                    steps {
                        sh 'mvn test'
                    }
                }

                stage('Security Scan') {
                    steps {
                        sh './security-scan.sh'
                    }
                }

                stage('Code Quality') {
                    steps {
                        sh './quality-scan.sh'
                    }
                }
            }
        }

        stage('Deploy') {
            steps {
                sh './deploy.sh'
            }
        }
    }
}
```

Use parallel execution only when tasks are independent.

## 13. Complete CI/CD Pipeline Example

```groovy
pipeline {

    agent any

    environment {
        APP_NAME = 'demo-app'
    }

    stages {

        stage('Checkout') {
            steps {
                checkout scm
            }
        }

        stage('Build') {
            steps {
                sh 'mvn clean package'
            }
        }

        stage('Parallel Validation') {

            parallel {

                stage('Unit Test') {
                    steps {
                        sh 'mvn test'
                    }
                }

                stage('Security Scan') {
                    steps {
                        sh './security-scan.sh'
                    }
                }
            }
        }

        stage('Docker Build') {
            steps {
                sh 'docker build -t $APP_NAME:$BUILD_NUMBER .'
            }
        }

        stage('Deploy') {
            steps {
                sh './deploy.sh'
            }
        }
    }

    post {

        success {
            echo 'Pipeline completed successfully'
        }

        failure {
            echo 'Pipeline failed'
        }

        always {
            echo 'Pipeline finished'
        }
    }
}
```

# 14. Jenkins Best Practices

## 14.1 Pipeline as Code

Store the Jenkinsfile in Git:

```text
Application Repository
│
├── src/
├── Dockerfile
├── pom.xml
└── Jenkinsfile
```

Benefits:

- Version control
- Code review
- Auditability
- Rollback
- Reproducibility
- Disaster recovery

---

## 14.2 Secure Credentials

Use:

```text
Jenkins Credentials Manager
```

instead of:

```text
Passwords in Jenkinsfile
Passwords in Git
Passwords in shell scripts
```

Use credential IDs:

```groovy
credentialsId: 'aws-prod'
```

Follow least-privilege access.

---

## 14.3 Use Agents

Bad architecture:

```text
Jenkins Controller
   |
   +-- Maven
   +-- Docker
   +-- Unit Tests
   +-- Security Scan
   +-- Deployment
```

Better:

```text
                 Controller
                     |
        +------------+------------+
        |            |            |
      Agent        Agent        Agent
      Maven        Docker       Security
```

Benefits:

- Protect controller resources
- Scale horizontally
- Isolate workloads
- Support different environments

---

## 14.4 Control Plugins

Plugins provide integrations for:

```text
Git
GitHub
Bitbucket
Docker
Kubernetes
AWS
Maven
SonarQube
Security tools
```

Installing too many plugins creates risks:

- Security vulnerabilities
- Dependency conflicts
- Compatibility problems
- Maintenance overhead
- Upgrade complexity

Recommended process:

```text
Need a plugin?
     |
     v
Is it really required?
     |
     +-- No → Don't install
     |
     +-- Yes
          |
          v
Check maintenance/security
          |
          v
Install approved plugin
```

Regularly review plugin versions and security advisories.

---

## 14.5 Jenkins Backups

Jenkins contains important state such as:

```text
Jobs
Credentials-related configuration
Plugin configuration
Global configuration
Nodes
Security configuration
Users
```

Back up Jenkins home and maintain tested recovery procedures.

Typical Jenkins home:

```bash
$JENKINS_HOME
```

A common installation may use:

```text
/var/lib/jenkins
```

but always verify the actual location.

Important areas may include:

```text
JENKINS_HOME
├── jobs/
├── credentials.xml
├── config.xml
├── nodes/
├── secrets/
├── plugins/
└── users/
```

**Important:** Jenkins secrets and credential-related files are sensitive. Protect backups with strong access controls and encryption.

### Backup strategy

```text
Jenkins
   |
   v
Scheduled Backup
   |
   v
Encrypted Backup Storage
   |
   +-- Daily
   +-- Weekly
   +-- Monthly
```

A backup should be periodically restored/tested to verify that it actually works.

# 21. Important Jenkins Interview Questions

### 1. What is Jenkins?

An automation server used for CI/CD, build automation, testing, deployment and orchestration.

### 2. What is a Jenkinsfile?

A file containing the Pipeline definition, normally stored in source control.

### 3. What is Pipeline as Code?

Managing pipeline configuration as version-controlled code instead of configuring it only through the Jenkins UI.

### 4. Declarative vs Scripted Pipeline?

Declarative uses structured syntax and is easier to maintain; Scripted uses Groovy and provides greater programming flexibility.

### 5. What is a Jenkins agent?

A machine where Jenkins executes pipeline workload.

### 6. Why should builds not normally run on the controller?

To protect controller resources and improve scalability, isolation and reliability.

### 7. What is a Jenkins credential?

A securely managed secret used by Jenkins to authenticate to external systems.

### 8. Why shouldn't passwords be stored in Jenkinsfiles?

Because source code is version controlled and may expose sensitive information.

### 9. What is a webhook?

An HTTP notification sent by a system such as GitHub or Bitbucket to Jenkins when an event occurs.

### 10. Webhook vs Polling?

```text
Polling:
Jenkins → Git → "Any changes?"

Webhook:
Git → Jenkins → "Code changed!"
```

### 11. What is parallel execution?

Running independent pipeline stages simultaneously to reduce overall execution time.

### 12. What is `agent any`?

It allows Jenkins to execute the pipeline on any suitable available agent.

### 13. Why control Jenkins plugins?

To reduce security, compatibility, maintenance and upgrade risks.

### 14. Why back up Jenkins?

To recover jobs, configurations, nodes and other Jenkins state after failure.
